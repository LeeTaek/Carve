# Carve 2.0.0 로드맵

작성·갱신: 2026-09-17 · 목표 버전: **2.0.0** · 개정: 의존관계·출시 운영 반영 · 상태: 브랜치별 구현 예정

## 1. 목표와 현재 위치

> **더 편안하게 성경을 필사하고, 내가 쓴 말씀을 이미지와 위젯으로 곁에 두는 Carve 2.0.0.**

단일 Canvas 전환을 바탕으로 필사 도구와 차트의 사용성을 개선하고, 업데이트 안내와 일관된 디자인, 절 이미지 저장·필사 위젯, 앱 성격에 맞는 수익화 모델을 갖춰 2.0.0으로 출시한다. 출시일은 아직 정하지 않았다.

- 단일 Canvas 전환은 `develop`에 병합됐으며 기본값은 on이다. 사용자의 명시적 off 설정은 유지된다.
- Production CloudKit 스키마 승격과 주요 전환 결함 수정은 기존 기록상 완료됐다.
- 이번 문서 정리는 새로운 실기기 검증이나 테스트 실행이 아니다. 기록된 회귀 기준선은 312이며, 이후 변경에서 관련 검증 결과를 갱신한다.
- 이번 작업에서 앱 버전·빌드 번호는 변경하지 않는다. 통합 후보 빌드 준비 단계에서 버전을 2.0.0으로 변경하고, 검증한 빌드를 출시한다.

## 3. 작업 트랙과 선행 조건

표의 ID는 순번이 아니다. 디자인·콘솔 조사·호환성 결정·위젯 위험 확인은 초기에 시작하고, 구현은 선행 조건이 충족된 작업 중에서 선택한다. 한 번에 한 브랜치씩 작업해도 외부 결정 대기 때문에 독립 작업을 멈추지 않는다. 트랙 구분은 동시 코딩이나 여러 에이전트 실행을 요구하지 않는다.

작업 시작 시 최신 `develop`에서 목적별 브랜치를 만든다. 실제 의존하는 PR의 반영은 기다리되 모든 앞 행의 병합을 기다리지는 않는다. 같은 화면·저장 경로를 수정하는 작업은 겹치지 않게 조율한다. 검증·제한을 한글 PR에 기록하며 머지는 별도 요청에 따른다. 아래 브랜치는 제안이고 아직 생성하지 않았다. DOC(기존 문서 정리)는 작성 완료, 나머지는 예정 또는 결정 대기다.

새 기능은 프리즈 이후 다음 버전으로 넘긴다. 결함 수정은 가능하나 후보 빌드와 검증 기록을 갱신한다. TestFlight는 미보유 구기기·120Hz 테스터 확보를 요구하는 게이트가 아니다. 코드 프리즈·통합 검증·TestFlight·심사에는 반복이 있을 수 있으며 수정한 빌드를 검증 없이 출시하지 않는다.

### 절 롱탭 메뉴·이미지 저장·필사 위젯

2026-09-09 사용자 원기획을 확인해 **2.0.0 범위에 포함**했다. 메뉴는 한 절을 대상으로 `이전 필사 보기 | 이미지 저장 | 위젯에 추가 | 삭제`를 제공한다. 메뉴와 이미지 코어는 독립적으로 준비할 수 있다. 메뉴 연결과 공통 코어를 바탕으로 사진 저장·위젯을 완성한다.

| 메뉴 | 2.0.0 동작과 범위 |
|---|---|
| 이전 필사 보기 | 현재 제공하는 이전 필사 보기 유지. 여러 회차를 보관하는 완전한 버전 이력으로 확장하지 않음 |
| 이미지 저장 | 선택한 절의 성경 본문·필기를 합성해 사진으로 저장. 권·장·절 식별 정보를 포함하고 선택 UI·도구·광고는 제외 |
| 위젯에 표시 | 선택한 절의 **지정 당시 이미지**를 홈 화면 위젯의 표시 대상으로 저장. 이후 필기를 수정해도 자동 반영하지 않고 다시 지정하면 교체 |
| 삭제 | 해당 절의 필사 삭제. 확인창에서 권·장·절과 삭제 범위를 명시하고 성경 본문과 다른 절의 필사를 보존 |

위젯의 첫 범위는 **공통으로 선택한 절 하나**이며, 탭하면 앱의 해당 절로 이동한다. 여러 절 순환·위젯 인스턴스별 별도 선택·편집 실시간 동기화는 포함하지 않는다. 앱 메뉴는 위젯의 표시 대상을 지정하는 동작이므로 홈 화면에 위젯을 자동 추가했다고 안내하지 않는다. 아직 추가하지 않은 사용자에게 추가 방법을 안내한다.

이미지와 위젯은 같은 절 이미지 생성 경로를 사용한다. 화면 캡처에 의존하지 않고 저장된 필기와 본문 배치를 맞추며, 진행 중 편집이 있으면 일관된 결과를 얻는 시점에 생성한다. 절 경계를 넘는 획은 기존 소유권 규칙을 바탕으로 표시·잘림 정책을 정하고 인접 절 필기 혼입을 검증한다.

위젯 크기와 긴 절 표현 방향은 DESIGN-0·WIDGET-0에서 일찍 정하고 DESIGN-1에서 마감한다. 임의로 글자를 지나치게 축소하거나 잘라 전체 내용처럼 보여주지 않는다. 앱 재실행·위젯 미지정·이미지 교체·이미지 생성 실패를 확인한다. 위젯을 탭해 앱으로 돌아와도 현재 편집 내용을 유실하지 않아야 한다.

⚠️ **WIDGET-0에서 두 가지가 추가로 확인됐다 (2026-09-10).** ① **위젯은 앱 Info.plist의 `UIUserInterfaceStyle: Light`를 상속하지 않는다.** 홈 화면의 라이트/다크를 따라가며, 위젯 자신의 Info.plist에 같은 키를 넣어도 무효다. "지정 당시 이미지"를 흰 배경 전제로 렌더하면 다크에서 검은 카드 위에 흰 사각형이 뜬다. 배경을 명시 색으로 칠하고 뷰에서 colorScheme을 다뤄야 한다. **위젯 완료 기준에 라이트·다크 양쪽 확인을 포함한다.** ② **WidgetKit은 위젯에 넣는 이미지의 면적에 상한을 둔다** — 초과하면 앱은 정상인데 위젯만 조용히 플레이스홀더로 남는다. 사진 저장용 원본을 위젯에 그대로 줄 수 없으므로 IMAGE-CORE가 위젯용 축소 사본을 함께 만들지 결정한다. 근거는 [위젯 위험 확인](./widget-feasibility.md) §2·§4.

**구현 전 세부 결정:** 절 삭제가 이전 필사 기록까지 포함하는지, 원본 삭제 후 위젯의 별도 이미지를 유지할지 제거할지, 위젯 표시 해제 위치. 위젯이 지정 시점의 별도 사본이라는 점과 삭제의 영향 범위를 사용자에게 일관되게 안내한다.

위젯 구현에는 전용 타깃과 앱·위젯 간 공유 저장 구성이 필요할 수 있다. 기존 설정 변경 금지 원칙의 일반 리팩터링과 구별해 WIDGET 브랜치의 기능상 필요한 범위로 명시하고, Tuist 구성·entitlement·서명 영향을 확인한다. 관련 없는 의존성이나 빌드 설정 변경은 섞지 않는다. **WIDGET-0에서 확인했다** — 기존 `makeAppTarget` 관용구로 app extension 타깃을 만들 수 있고 서명은 프로젝트 레벨 자동 서명을 그대로 상속한다. 공유 저장은 App Group `group.kr.co.carve.leetaek` 하나면 되고 위젯에 SwiftData·CloudKit을 링크하지 않는다. 다만 **App Group은 개발자 포털 등록이 남아 있다**(계정 변경이라 미수행). 필요한 설정 목록은 [위젯 위험 확인](./widget-feasibility.md) §5.

**즐겨찾기 (2026-09-15 추가).** 절 메뉴 첫 항목 `즐겨찾기에 추가 | 즐겨찾기 해제`, 절 번호 아래 별 표시, 사이드바 별 버튼과 목록(시안 N1~N5, [UI 방향](./design/ui-design-direction.md) §5). 결정 두 가지:

- **보관 단위 — 추가 당시 보존.** 추가하는 순간의 본문·필기(저장 대기 중인 획 포함)를 복사해 두고 원래 필사 행을 참조하지 않는다. 이후 절을 지우거나 다시 써도 카드는 바뀌지 않고, 해제해도 원래 필사·이전 기록은 지우지 않는다. 번역본·권·장·절마다 한 항목이다.
- **저장 — SwiftData V5 `FavoriteVerse` + CloudKit 동기화.** V4 → V5 lightweight, `BibleDrawing` 무변경. **V4 에 끼워 넣지 않은 이유:** 이미 V4 로 열린 개발·검증 store 가 staged migration 에서 `unknown model version`(134504)으로 열리지 않았다(2026-09-15 SwiftData 단독 실험 — 출시본 V3 store 는 두 방식 모두 열림). CloudKit 은 unique 제약이 없어 두 기기가 같은 절을 따로 추가하면 행이 둘이 될 수 있고, 저장소가 키로 합친다.
- **V5 가 없는 이전 빌드 — 지금대로 둔다(2026-09-15 사용자 결정).** 이미 빌드된 V4 빌드가 V5 로 올라간 store 를 열면 staged migration 이 `134504` 로 거부하고(실험 확인) 앱은 V1 폴백을 거쳐 `fatalError` 로 끝난다.
  ⚠️ **2026-09-16 정정 — 출시본(1.3.0 · V3)에서는 결과가 다르다.** 같은 `134504` 가 나지만 **V1 폴백이 성공해서** `fatalError` 에 도달하지 않는다. 저장소가 `DrawingVO` 스키마로 갈아치워지고 기존 필사가 사라진 채 **앱은 평소처럼 열린다**(시뮬레이터 실측, [테스트 계획](./icloud-sync-compatibility-test-plan.md) §5-1 DOWN-L2 · F7). `fatalError` 는 사용자가 즉시 알아채지만 이쪽은 **조용한 데이터 소실**로 보이므로, "지금대로 둔다" 는 결정이 전제한 위험도와 다르다. 폴백 성공 여부는 빌드 조합마다 달라지므로 조합별로 다시 확인한다. 설치된 빌드의 코드는 바꿀 수 없어 막지 않는다 — V4 가 V3 빌드에 대해 가진 forward-only(설계 §10-3)와 같은 성질이다. App Store 는 이전 버전을 설치할 수 없어 운영 영향은 TestFlight 에서 예전 빌드를 다시 까는 경우뿐이고, 개발 기기 · 시뮬레이터는 V5 없는 브랜치로 바꿀 때 앱을 지웠다 다시 깐다. 검토했다가 택하지 않은 안: 개발 빌드 저장소 파일을 스키마 버전별로 분리 · 새 스키마 저장소를 만나면 크래시 대신 업데이트 안내 · 즐겨찾기를 별도 저장소로 분리.

N-Canvas(flag off) 경로에는 별 표시만 보이고 추가·해제 메뉴는 없다 — 그 경로의 메뉴는 `이전 필사 내용 보기` 하나다(`지우기` 와 같은 범위).

**이미지 저장 (2026-09-15 추가).** 절 메뉴 `이미지 저장` 을 켰다(시안 G1 · G2). 캔버스가 넘긴 그 절의 필사 영역(폭 · 밑줄)과 지금 보이는 필기(저장 대기 중인 획 포함, 화면처럼 현재 밑줄에 재배치한 모습)에 본문 · 본문 모양 · 출처를 더해 SwiftUI `ImageRenderer` 로 PNG 를 만들고 사진 보관함에 넣는다. 결정:

- **사진 권한 — 추가 전용(2026-09-15 사용자 결정).** `PHAccessLevel.addOnly` 만 요청하고 보관함을 읽지 않는다(Info.plist `NSPhotoLibraryAddUsageDescription`). 그래서 G2 캡션의 「새기다」 앨범은 만들지 않고 최근 항목에 들어간다.
- **필기가 없는 절 — 본문만 담아 저장(2026-09-15 사용자 결정).** `나의 필사` 칸을 뺀다.
- **배치.** 본문 위 · 필기 아래(G1). 필기 칸은 캔버스 필사 영역과 같은 폭 · 같은 밑줄이다. 절 경계를 넘는 획은 소유한 절에 통째로 담기므로 자르지 않고 칸을 늘린다(본문 폭보다 넓어지면 비율을 지켜 줄인다). 늘 종이(라이트) 외관이다(문서 8-1).
- **출처 표기.** G1 은 `시편 23편 1절` 이지만 헤더 · 즐겨찾기와 같게 `시편 23장 1절 · 개역한글` 로 적는다.
- **결과(G2).** 성공 `사진에 저장했어요`(2초), 실패 `저장하지 못했어요` + `다시 시도`(5초), 권한 거부는 `사진 접근이 꺼져 있어요` 확인창(`나중에 | 설정 열기`). 안내 자리는 즐겨찾기 안내와 하나를 나눠 쓴다.
- 절 메뉴가 단일 Canvas 경로에만 있어 N-Canvas(flag off)에는 없다. 위젯용 축소 사본(WidgetKit 면적 상한)은 만들지 않았다 — WIDGET 에서 정한다.

**필사 위젯 (2026-09-16 추가).** 즐겨찾기를 보관함으로 쓰고 그중 **여러 말씀**을 골라 홈 화면 위젯에 돌려 표시한다(시안 N6~N9, [UI 방향](./design/ui-design-direction.md) §5). WIDGET-0 에서 검증한 구성을 그대로 되살렸다 — 위젯 타깃 · App Group · `carve` URL 스킴. 결정:

- **선택은 기기별(2026-09-16 사용자 결정).** 위젯이 읽는 이미지가 그 기기의 App Group 안에 있어 iCloud 로 맞추지 않는다. App Group 의 작은 JSON 하나가 선택의 진실이고 앱 화면(카드 배지 · 설정)도 그 값을 읽는다.
- **크기는 중간 하나다(2026-09-16 사용자 결정).** 처음에는 작게 · 중간을 냈다가, 작게(`systemSmall`)는 말씀 한 줄도 좁아 같은 날 빼고 `systemMedium` 만 낸다.
- **위젯이 읽는 것은 지정 당시 사본뿐이다** — 권 · 장 · 절 · 번역본 · 본문과 필기 PNG. Domain · SwiftData · CloudKit · TCA 를 위젯에 링크하지 않는다(WIDGET-0 §2). 이후 원래 필사를 고치거나 지워도 위젯은 바뀌지 않는다.
- **필기 PNG 는 크기를 줄여 담는다.** WidgetKit 은 이미지 면적 상한을 넘으면 조용히 빈 칸으로 남는다(WIDGET-0 §2 — systemSmall 에서 면적 349,905 관측). 여러 말씀을 돌리면 한 타임라인이 그림을 여러 장 들고 있어 420 × 260pt 로 둔다.
- **다크에서도 종이.** 위젯은 앱의 라이트 고정을 상속하지 않으므로 배경을 종이색으로 명시하고 뷰에 라이트 `colorScheme` 을 넣는다(WIDGET-0 §4 · 문서 8-1).
- **진입점 셋이 같은 선택을 쓴다.** 절 롱탭 「위젯에 추가」(즐겨찾기에 없으면 지금 모습을 보관하고 담기 — 「즐겨찾기에 추가하고 위젯에 담았어요」), 즐겨찾기 카드 더보기(N6), 설정 → 위젯(N7, 고르는 시트 N8).
- **담긴 즐겨찾기를 해제하면** 위젯에서도 빼고 다른 말씀을 자동으로 채우지 않는다. 해제 전에 확인한다(N9). 나머지 말씀은 그대로 돈다.
- **위젯을 누르면** `carve://verse?...` 로 그 절의 필사 화면으로 간다. 콜드 런치면 준비 화면이 끝난 뒤 이동한다.
- **여러 말씀을 담아 돌린다(2026-09-16 사용자 결정).** 최대 20개까지 담고 **1시간마다** 한 말씀씩 넘어간다. 매번 새로 뽑지 않고 **한 바퀴**를 섞어 돌아 한 바퀴 안에서는 겹치지 않고, 바퀴가 바뀔 때도 직전 말씀이 연달아 나오지 않는다([WidgetVerseRotation](../Domain/Domain/Sources/Widget/WidgetVerseRotation.swift)). 순서는 칸 번호를 씨앗으로 한 결정적 셔플이라 위젯이 다시 그려져도 튀지 않는다.
- **순서 규칙은 Domain 이 갖고 위젯이 소스로 함께 컴파일한다.** 위젯은 Domain 을 링크하지 않지만(WIDGET-0 §2) 규칙이 둘로 갈라지지 않도록 그 파일 하나만 타깃에 넣고 Domain 테스트로 지킨다.
- **타임라인은 6칸(6시간)씩 만든다.** WidgetKit 은 타임라인의 모든 칸을 한꺼번에 들고 있어 칸마다 올린 필기 그림이 그대로 익스텐션 메모리가 된다. 하루치를 한 번에 만들지 않고 `.atEnd` 로 이어 받는다(하루 4회 — 시스템 새로고침 예산에 여유가 있다). 필기 그림 상한도 560 × 360pt 에서 **420 × 260pt** 로 줄였다.
- 위젯별 개별 선택(위젯마다 다른 목록) · 순환 주기 설정은 후속 범위다.

### 본문 모양 iCloud 백업

**2026-09-15 추가.** 글꼴 · 글자 크기 · 줄 간격 · 자간을 iCloud 키-값 저장소(`NSUbiquitousKeyValueStore`, 키 `sentenceSettingBackup`)에 올려 두고, 앱을 지웠다 다시 깐 기기에서 되살린다([SentenceSettingCloudBackup](../Domain/Domain/Sources/SentenceSettingBackup/SentenceSettingCloudBackup.swift)). 결정:

- **저장 — SwiftData V5 가 아니라 키-값 저장소(2026-09-15 사용자 결정).** 기기 설정 네 값이라 스키마 · 마이그레이션 · CloudKit 운영 배포가 필요 없다. entitlement `com.apple.developer.ubiquity-kvstore-identifier` 를 추가했다.
- **되살리는 때 — 아직 안 바꾼 설치에서만(2026-09-15 사용자 결정).** 새 설치(재설치 포함)는 본문 모양을 바꾸기 전까지 iCloud 값을 받고, 실행 뒤 늦게 내려온 백업도 적용한다. 한 번이라도 바꾼 설치는 자기 값을 지키고 올리기만 한다. 설치 판정은 `UserDefaults` 키 `sentenceSettingUserChosen` 에 남긴다 — 본문 설정은 처음 읽을 때 기본값이 저장되므로 Store 를 만들기 전에 판정한다.
- **올리는 때 — 사용자가 값을 실제로 바꿀 때만.** 실행만으로는 올리지 않는다(새로 깐 기기의 기본값이 백업을 덮지 않게). 슬라이더를 건드리기만 한 것도 바꾼 것으로 치지 않는다. 왼손 모드 · 손가락 필사는 기기마다 달라 백업하지 않는다.
- **이 기능 전부터 쓰던 설치**(1.x · 이전 2.0 빌드 — 저장된 본문 설정이 있음)는 바꾼 설치로 보고, iCloud 에 백업이 없을 때만 지금 값을 한 번 올린다. 1.x 에서 설정을 건드리지 않았다면 그때 기본 글꼴(나눔바른고딕)이 올라가 재설치해도 쓰던 모습으로 돌아온다. 두 기기에서 따로 바꾸면 마지막에 올린 값이 남는다.

### 영어 성경 추가 — BIBLE-EN

2026-09-09 사용자 계획을 반영한 별도 기능 항목이다. **WEB(World English Bible)** 및 **KJB(King James Bible, 통상 KJV로 표기)**를 후보로 삼는다. 정확한 판본과 수록 범위는 아직 결정하지 않았다. 2.0.0 포함 여부는 SCOPE에서 확정하고, 이 항목 추가만으로 두 번역본 동시 출시를 필수 조건으로 삼지 않는다.

- **판본·권리 확인:** WEB는 공식 사이트가 본문을 public domain으로 제공한다. 명칭·로고는 충실한 사본을 식별하는 용도로 사용하도록 안내한다. WEB도 여러 판본이 있으므로 언어 표기·포함 성경 권수·배포 파일 버전을 고정한다. KJB/KJV는 영국 내 Crown 권리와 허가 조건이 있어 전 세계에서 일괄적으로 권리가 만료됐다고 전제하지 않는다. 광고·유료 기능이 있는 앱 배포, 이미지 저장·위젯 표시를 포함한 실제 용도와 배포 지역을 확인한다. 제공 파일의 주석·소제목 등 부가 자료 조건도 본문과 구별한다.
- **콘텐츠 수록:** 신뢰할 수 있는 원문 출처와 판본·취득일을 기록하고, 권·장·절 식별·누락·문자 인코딩을 검증한다. 필요한 출처·권리 안내를 앱에 포함한다. 첫 판본은 WEB 우선 검토, KJB/KJV는 권리·출처 확인 후 선택한다.
- **사용자 동작:** 번역본 선택과 현재 번역본 표시를 제공한다. 앱 전체 UI의 영어 현지화, 한영 대조 화면, 자동 번역은 이 항목의 범위에 포함하지 않는다.
- **필사 데이터 보존:** 같은 권·장·절이라도 번역본이 다른 필사는 섞이지 않도록 귀속 정책을 먼저 정한다. 기존 한국어 필사의 식별·저장·동기화를 보존하고, 번역본 전환 시 저장·복원 및 차트·최근 기록·이전 필사·삭제 범위를 명확히 한다. 단순 본문 파일 교체 작업으로 취급하지 않는다.
- **COMPAT-0에서 확인한 사실 (2026-09-09):** `translation` 필드는 V2부터 스키마에 있어 **새 필드 추가는 불필요**하다. 그러나 `Translation` enum은 `NKRV` 하나뿐이고 **`BibleDrawing` 조회 술어 8곳이 전부 번역본을 보지 않는다** — 지금 구조로 영어를 넣으면 같은 절의 한국어·영어 필사가 한 행 집합이 된다. 행 `id`에도 번역본이 없고 성경 이름 자리에 **본문 파일명**이 들어간다. 본문 로더는 EUC-KR·`\r` 고정이라 판본별 인코딩·줄 구분 분기가 필요하고, 번역본 차원은 파일명이 아니라 **경로**로 넣어야 한다. 근거와 선택지는 [데이터 호환성 결정](./data-compatibility-decision.md) §1·§4-3.
- **구버전 영향:** 구버전은 번역본을 모르므로 2.0.0이 쓴 영어 행을 그 절의 한국어 필사로 읽고 편집할 수 있다. `Translation`에 case를 추가하는 것 자체도 구버전의 디코딩 실패를 부를 수 있어, R28과 같은 자리에서 판단한다.
- **다른 기능과 연결:** 영어 단어 줄바꿈·긴 절·폰트·밑줄·회전을 확인한다. 이미지와 위젯의 출처 표기·대상 식별에 번역본을 포함하고, 위젯을 탭하면 해당 번역본의 절로 이동한다. 번역본 식별 정책은 IMAGE-CORE·WIDGET의 대상 식별 설계 전에 공유하되, 영어 본문 전체 구현 완료를 그 작업의 선행 조건으로 두지는 않는다.
- **완료 기준:** 원문·권리 근거 기록, 번역본 전환 후 한국어/영어 필사 혼입 없음, 기존 한국어 데이터 회귀 없음, 영어 본문과 이미지·위젯의 일치. 스키마 변경이 필요하면 데이터 호환성 검토와 마이그레이션 검증을 별도로 포함한다.

### 업데이트 안내

NEWS-CORE는 표시 기능, NEWS-CONTENT는 실제 2.0.0 문구다. 기능은 먼저 검증하고 문구는 SCOPE 이후 확정한다.

- 앱 시작 직후 필기나 다른 필수 화면을 가로막지 않는 안정된 시점에 표시한다.
- 콘텐츠는 초기에는 앱 번들에 포함한다. 원격 배포 시스템은 현재 범위에 넣지 않는다.
- 최초 설치는 별도 환영 안내와 구분한다. 제안 기본값은 신규 설치에서 패치노트 자동 노출 생략, 기존 설치 업데이트에서 한 번 노출이다.
- 이전 확인 버전이 없는 기존 사용자를 어떻게 구분할지 구현 전에 정한다. 이 정보가 없으면 정확한 신규/업데이트 구분을 보장한다고 쓰지 않는다.
- 버전을 여러 개 건너뛴 경우 최신 릴리스의 핵심 변경을 보여주고, 설정에서 다시 열 수 있게 한다.
- 표시 상태와 확인한 릴리스 ID는 Feature 상태·Action으로 관리하고, 버전 조회·확인 기록 저장은 Dependency/Effect로 처리한다.

### 사용법과 발견성

HELP가 최초 진입의 짧은 안내와 설정에서 다시 보는 도움말을 관리한다. 두 손가락 스크롤, 절 롱탭 네 메뉴, 이미지 저장, 위젯 지정과 홈 화면 추가 방법을 한 흐름으로 정리한다. 패치노트는 바뀐 점을 소개하고 필요한 도움말로 연결한다. 안내는 건너뛸 수 있고 필기 영역을 지속해서 가리지 않는다. 첫 설치 환영 안내를 별도 대형 온보딩으로 확장하지 않는다.

### 디자인

목표는 성경 본문과 필기가 중심인 차분하고 정돈된 화면이다. Bear의 본문 중심 계층과 차분한 여백을 주요 레퍼런스로 선정했다. 합의한 방향, 색상·타이포 초안, Figma 프레임, 큰 글꼴·성경/장 탐색 SVG와 미검증 항목은 [디자인 방향과 시안](design/ui-design-direction.md)에 정리했다. 현재는 초안 단계이며 DESIGN-0 전체 완료나 앱 구현 완료를 의미하지 않는다.

공통 색상·글자 크기·간격·카드·버튼 상태부터 정한다. 한 번에 모든 화면을 재구성하지 않고 필사 → 차트·설정 순으로 적용한다. 가로·세로·좁은 창, 대비와 터치 영역, 지원하는 글자 크기에서 확인한다.

### 광고와 수익화

처음에는 광고 제거 일회성 구매 또는 필사를 명시적으로 끝낸 결과 화면의 광고를 후보로 두었다. **결정 (2026-09-14): 광고 확대 + 광고 제거 일회성 구매.** 먼저 탐색 사이드바 하단(시안 K3)과 필사 헤더 줄(시안 K2)에 네이티브 광고를 넣고, 이어서 광고 제거 구매를 붙인다. 장 완료 화면을 만들지 않으므로 결과 화면 광고 후보는 빠졌다([디자인 §8-2](design/ui-design-direction.md)). 광고 제거 가격은 아직 정하지 않았다.

- 기존 차트 광고의 노출·수익·이용 규모를 확인하고 추가 광고의 효과를 추정한다.
- 장 전환마다 전면 광고는 계속 제외한다. **필사 중 상시 광고는 헤더 줄 네이티브 광고로 채택했다(2026-09-14, 사용자 결정 — 필사하는 동안 헤더가 화면에 머무는 시간이 길다).** 필기 열 옆 배너처럼 필사 폭을 바꾸는 자리는 쓰지 않는다.
- ⚠️ **헤더 광고는 AdMob 배치 가이드와 겹치는 점이 남는다** — 내비게이션 버튼 옆, 사용자가 계속 조작하는 화면, 스크롤에 따라 광고 크기가 바뀜(56 ↔ 44pt). 정책 경고나 게재 제한이 오면 높이 고정이나 자리 이동부터 검토한다. 근거: [AdMob 배치 가이드](https://support.google.com/admob/answer/6275345), [네이티브 광고 정책](https://support.google.com/admob/answer/6329638).
- 구독은 지속 제공할 유료 가치가 정해졌을 때 별도 검토한다.
- 광고 제거를 선택하면 구매·복원·취소·오프라인 권한 처리와 기존 광고 노출 중단을 검증한다.
- 광고 확대를 선택하면 노출 조건·빈도·실패 시 화면·광고 표시·오터치 방지를 검증한다. 수익뿐 아니라 필사 완료·재방문 변화도 함께 본다. 필요한 집계 이벤트는 해당 브랜치에서 설계하며 필사 내용 자체를 수집하지 않는다.
- 성적 주제 등 민감 카테고리 차단, 최대 콘텐츠 등급 G, 개별 광고 검토를 함께 운영한다. **민감 카테고리 차단은 AdMob 콘솔에 설정했고(2026-09-14, 사용자) 콘텐츠 등급 G는 앱이 모든 광고 요청에 적용한다.** 필터만으로 부적절한 광고가 전혀 나오지 않는다고 보장하지 않는다.
- AdMob 콘솔 설정은 앱 코드와 별도로 확인한다. **동의 흐름은 UMP로 넣었다(2026-09-14)** — 앱을 실행할 때마다 동의 정보를 갱신하고, 동의가 필요한 지역(EEA·영국·스위스)에서만 폼을 띄운다. 광고를 요청해도 되는 것이 확인된 뒤 광고 SDK를 시작하고, 설정에 광고 개인정보 옵션 진입점을 둔다. ❓ 콘솔의 GDPR 메시지 게시와 실기기 폼 표시는 확인하지 않았다. ATT 프롬프트는 두지 않았다(IDFA 추적을 요청하지 않는다).

앞선 조사에서 확인한 공식 참고 자료(구현 시 재확인): [AdMob 차단 옵션](https://support.google.com/admob/answer/3150235?hl=en), [iOS 최대 광고 콘텐츠 등급](https://developers.google.com/admob/ios/targeting), [광고 검토 센터](https://support.google.com/admob/answer/3480906?hl=en).

R27·R28은 저사양·120Hz 문제와 다르다. 보유한 두 기기로 확인할 수 있지만 이번 문서 정리를 위해 재검증을 요구하지 않는다. MetricKit은 중복 행이나 필기 좌표 오류를 판정하지 못한다.

⚠️ **UI-2의 "지우기"가 R27·U4의 검증 범위를 넓혔다 (2026-09-09).** 지우기는 삭제가 아니라 현재 필사를 보관 행으로 남기고 활성 행을 비우므로 **절당 행이 의도적으로 하나씩 늘어난다.** 그 전까지 이 앱은 회차가 쌓이지 않는 설계였고 "이전 필사 보기"는 이력이 아니라 데이터 생존 확인용 안전망이었다(런북 D9-5-4·5-5가 "판정 불가"로 남은 이유). **지우기는 이전 기록을 실제로 쌓기 시작하는 첫 기능이다.** D2·D6를 나중에 확인할 때 보관 행과 두 기기 중복 행의 구별, 보관 행 `rowUUID`의 구버전 왕복 보존, 보관+초기화가 CloudKit에 레코드 2개로 따로 전파되는 중간 상태를 범위에 포함한다. 새 위험 판정이 아니라 기존 미확인 항목의 범위 확대다 — 근거는 [데이터 호환성 결정](./data-compatibility-decision.md) §5-1.

✅ **출시본이 확정됐다 (COMPAT-0, 2026-09-09).** App Store 판은 **1.3.0 (177) · 2026-03-23 빌드**이며 저장소의 `49f2dc27`에 해당한다. 그 시점 스키마는 **V1·V2·V3뿐이고 V4가 없다** — V4(`b68b6101`)보다 5개월 앞선다. 즉 기존 문서의 "출시본은 V4 스키마까지"라는 전제는 틀렸고, `1.3.1`은 출시된 적 없는 준비 버전이었다. 정정의 영향은 셋이다. **R28은 등급 유지** — 출시본이 `drawingVersion`을 편집 시 쓰지 않아(쓰는 곳은 마이그레이션 한 줄과 모델 기본값뿐) 라벨 3이 남는 메커니즘이 코드로 재확인됐다. **R27은 범위 확대** — 출시본에 `rowUUID` 필드 자체가 없어 앞으로도 발급하지 못하므로, 구버전이 살아 있는 동안 rowUUID 없는 행이 계속 늘어난다. **U4(구버전 쓰기가 서버의 V4 필드를 보존하는가)가 새로 중요해졌다.** 근거는 [데이터 호환성 결정](./data-compatibility-decision.md) §3.

R28의 업데이트 안내는 완화 수단일 뿐이다. 새 버전의 팝업이 구버전 기기의 편집을 차단하지는 않는다. 단계적 출시 역시 혼재 버전을 없애지 않으므로 그것만으로 해결 완료로 표시하지 않는다. 최종 대응은 COMPAT-0에서 초반에 결정하고 필요한 작업은 COMPAT-1에서 처리한다. 새 버전에 최소 버전 게이트를 추가하는 것만으로 이미 배포된 구버전을 제어할 수 있다고 가정하지 않는다.

## 6. 검증·베타·출시 후 대응

보유 기기는 **iPad mini 7세대(A17 Pro), iPad Air M2 11인치**다. 구기기·120Hz 기기는 직접 검증할 수 없으며, 그 확보를 출시 선행 조건으로 삼지 않는다. 현재 기록된 실기기 결과는 mini 기준이며 Air의 과거 미수행 결과는 그대로 남긴다.

브랜치별로 가장 좁은 관련 검증부터 수행한다. 도구는 CLI 중심이며 **기준 툴체인은 Xcode 26.3 / 17C529 (Swift 6.2.4)**다 — TECH-0의 TCA 업데이트를 이 툴체인에서 검증했고 Xcode 27 beta는 확인하지 않았으므로 당분간 26.3을 계속 쓴다. Tuist는 `mise x -- tuist`로 실행한다. 테스트 destination은 iPad만 사용한다. 문구·중복 UI 제거에 구현을 그대로 따라 쓰는 테스트는 추가하지 않는다. 제스처와 필기 데이터에 영향이 있는 변경은 재현 동작·취소·저장 왕복을 확인한다.

**회귀 기준선 운영:** 각 PR은 가장 좁은 관련 검증을 수행하고, 캔버스·저장·공통 레이아웃 변경은 영향받는 회귀 범위를 확대한다. 문서·단순 문구 변경까지 312개 전체 실행을 요구하지 않는다. INTEGRATION 후보에서는 기존 312개와 이후 추가 테스트 전체를 검증한다. 기존 테스트 삭제·비활성화를 다른 테스트 수로 상쇄하지 않는다. 실패가 없어야 하며 실행 수 감소는 원인을 확인한다. 실행하지 못한 명령·이유는 남기고 통과로 표시하지 않는다.

**통합 스모크:** 보유 기기 두 대에서 디자인 × 팔레트 × 회전·좁은 창, 필기·저장 × 절 삭제·이미지 생성, 위젯 지정·재지정 × 앱 종료·재진입, 업데이트 안내 × 동의 화면의 순서를 확인한다. 긴 장에서 이미지 생성 전후·회전·위젯 진입의 메모리도 확인하고 앱과 위젯의 동작을 구별한다. 이는 변경된 제품 흐름의 확인이며 과거 D1~D9 전체를 재수행하는 요구가 아니다.

| 검증 범주 | 확인할 내용 |
|---|---|
| 화면과 입력 | 팔레트 전체 접근, 회전·좁은 창·왼손 모드, 차트 가로/세로/대각선 조작 |
| 상태와 정책 | 업데이트 안내 1회 노출·다시 보기·버전 건너뛰기, 선택한 광고/구매 모델의 실패 처리 |
| 필기 보존 | 메뉴 오조작 방지, 변경 관련 필기·지우개·undo/redo·장 전환·재실행 복원 |

현재 `MetricKitReporter`는 `mk_daily`에 `mem_exit_fg`, `mem_exit_bg`, `mem_pressure_bg`, `exit_fg_normal`, 가능한 경우 `peak_mb`를 전송하고, 메모리 한도 종료가 있으면 `mk_memory_kill`을 보낸다. 구현 존재와 실제 Analytics 수신 성공은 구분한다. payload 매핑·수신의 실제 확인은 기존 기록상 미완료다.

출시 후 첫 주에 수신 여부와 앱 버전·기기별 조회 가능 여부를 먼저 확인한다. 데이터가 없으면 정상으로 판단하지 말고 수집 연결부터 점검한다. 이후 2~4주간 메모리 종료와 사용자 제보를 함께 검토한다. 종료 절대 건수만으로 회귀를 판단하지 말고 수신량·사용 규모를 함께 확인한다. 이는 확인 계획이며 자동 모니터는 아직 설정하지 않았다.

현재 전송 항목만으로 120Hz 프레임 품질·Pencil 지연·회전 표시 오류를 알 수 없다. 필요하면 별도 성능 계측이나 사용자 재현 자료를 추가한다. 실제 필기감은 미검증 상태로 유지한다.

### 베타·단계적 출시·스토어 준비

TestFlight에서는 후보 빌드 설치·기존 상태를 가진 앱의 업데이트·위젯·선택한 구매/광고 흐름을 확인한다. 외부 테스터가 있다면 절차와 알려진 제한을 전달하고 제보를 반영한다. 실제 사용자 필기를 파괴하는 오류 주입은 하지 않는다.

단계적 출시는 자동 업데이트 확산 속도를 조절하는 운영 선택이다. 수동 업데이트는 가능하며 혼재 버전을 없애지 않으므로 R28 해결로 간주하지 않는다. STORE-PREP에서 방식과 중단 판단자를 정하고 RELEASE에서 확정한다. 최초 해당 유형 IAP는 새 버전과 함께 제출해야 하므로 상품 준비를 구현 중 시작한다. 최종 자료는 실제 출시 기능과 일치시킨다.

공식 참고(운영 시 재확인): [TestFlight](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/), [단계적 출시](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases), [IAP 제출](https://developer.apple.com/help/app-store-connect/manage-submissions-to-app-review/submit-an-in-app-purchase).

### 관측 신호에 따른 대응

| 신호 | 판단·대응 |
|---|---|
| 저장 유실·좌표 손상·다른 절 삭제의 구체적인 제보 또는 재현 | 즉시 우선 조사. 데이터 손상이 재현되거나 근거가 충분하면 단계적 출시 중단 여부와 핫픽스를 판단. 재설치·데이터 초기화를 기본 안내로 사용하지 않음 |
| 새 버전 특정 기기에서 반복 종료·메모리 종료 증가 | 수신량·사용 규모·OS·버전·재현 조건을 함께 확인. 기준선 대비 악화가 확인되면 확산 중단·최적화 핫픽스 검토. 절대 건수 하나로 판단하지 않음 |
| MetricKit 이벤트 없음 | 정상으로 결론 내리지 않고 payload·Analytics 연결과 조회 조건부터 점검 |
| 위젯·이미지 저장만 실패 | 원본 필기 영향부터 확인. 안전한 우회 안내 및 해당 기능 핫픽스 판단 |
| 부적절한 광고 제보 | 광고 식별·차단·신고, 반복 시 해당 노출의 중단 방법 검토. 원격 중단 기능이 있다고 가정하지 않음 |

보편적인 수치 임계값은 현재 데이터 없이 만들지 않는다. 출시 전 조회 방법과 가용 기준선을 확인하고, 부족하면 제보·재현 중심으로 판단한다. 첫 주 수신 확인, 이후 2~4주 추세 확인을 기본으로 하되 데이터 손상 제보는 정기 확인일까지 기다리지 않는다. 운영 판단·실행 담당은 프로젝트 소유자이며 자동화·배포 중단은 아직 설정하지 않았다.

**Canvas off는 기본 복구 지침이 아니다.** N-Canvas의 정지 메모리가 더 높았고 저장 형식도 달라질 수 있다. 해당 결함에서 안전한 우회임을 확인한 경우에만 안내한다. 기본값 변경이나 앱 버전 다운그레이드를 원격 롤백처럼 취급하지 않는다.

각 작업 완료 시 §3 상태를 갱신하고 PR/커밋, 실제 검증 명령·결과, 이월 항목을 기록한다. 이 문서의 예정 브랜치는 생성·커밋·푸시·머지·배포를 수행했다는 뜻이 아니다.

- 기존 TCA + MicroArchitecture 모듈 경계를 유지한다.
- View의 직접 I/O를 피하고 외부 처리는 Client/Dependency + Effect에 둔다.
- PencilKit은 어댑터, SwiftData는 기존 Repository 경로를 따른다.
- 의존성·CI·signing·빌드 설정 변경은 일반 기능 작업에 섞지 않는다. 명시적으로 계획한 TCA 업데이트와 필요한 전이 의존성 변경은 TECH-0에서 처리한다. 출시 버전 변경은 RC에서 수행한다. 위젯에 필요한 타깃·공유 저장·서명 설정은 WIDGET-0에서 범위를 확인하고 해당 기능 브랜치에 한정한다.
- 관련 없는 변경을 되돌리지 않고 PR별 목적과 검증 근거를 명확히 남긴다.

## 9. 로드맵 검토: 추가 개선 제안

검토일: 2026-09-09. 로드맵과 관련 소스를 대조한 결과다. 검토 후 저장 안내·데이터 설정 오류/설명은 SAVE-1·2, 도움말은 HELP, 접근성은 UI·DESIGN의 정식 범위로 반영했다. §9-2·3의 나머지는 추가 후보다. 코드 경로에서 확인한 사실과 제품 제안을 구분했으며 실기기 오류 주입 검증은 수행하지 않았다.

### 9-2. 이미 있는 기능의 개선 후보

- **이어 쓰기:** 차트에 최근 절·장으로 이동하는 버튼이 이미 있다. 새 최근 기록 기능을 중복 구현하기보다 필사 진입 화면에서 바로 접근할 필요가 있는지 확인한다. 마지막 장 복원과 마지막으로 쓰던 절 위치 복원은 구별해서 검증한다.
- **문의와 문제 제보:** 현재 메일 작성은 기기 모델·OS·앱 버전을 포함하고 사진 첨부도 지원한다. 새 문의 시스템보다 메일 미설정 시 문의 주소/진단 정보 복사 경로, 재현 단계 안내, 문구 오타 수정을 먼저 검토한다. 필사 데이터 자동 첨부는 추가하지 않는다.
- **이전 필사 보기:** 기존 런북상 회차가 쌓이는 완전한 버전 이력이 아니다. 실제 제공 범위에 맞춰 이름·설명을 정리하고, 사용자가 언제든 과거 상태로 복원할 수 있다고 오해하지 않게 한다. 버전 이력 저장은 별도 기능이다.

근거: [주간 요약](../Feature/ChartFeature/Sources/Chart/DrawingWeeklySummaryView.swift), [의견 보내기](../Feature/SettingsFeature/Sources/Details/SendFeedback/SendFeedbackView.swift), [메일 구성](../Feature/SettingsFeature/Sources/Details/SendFeedback/MailComposeView.swift), [런북 D9-5](./phase-0a-d-device-test.md).

### 9-4. 반영 결과

저장 실패 안내·데이터 설정 오류/설명과 도움말을 정식 작업으로 반영했다. 디자인·수익화·호환성 결정과 위젯 위험 확인은 초반으로 옮기고, 이미지 코어를 디자인 마감에서 분리했다. 업데이트 안내는 표시 기능과 실제 문구를 나눴다. §3의 선행 조건을 기준으로 작업하고 §7에서 범위 확정·통합 검증·베타·스토어 준비를 확인한다. 출시 후에는 §6의 관측 신호를 대응 판단으로 연결한다.
