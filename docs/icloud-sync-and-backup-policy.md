# iCloud 동기화·오프라인 사용·외부 백업 정책

작성·갱신: 2026-09-18 · 목표: **2.0.0** · 상태: **설계 기준선 확정 / 검증 조건부 구현 / 미구현·미검증** · §12-5 확정 전 설계 조건 · §12-6 C3 · C7 · C11 규칙 초안 v4(2026-09-18 · 구현 착수)

> **2026-09-16 범위 변경 — 외부 파일 백업·불러오기(§6·§7)는 2.1 로 이관한다.** 아래 백업 관련 결정(유료 권한·암호화·계정 제한 없는 불러오기)은 **내용 그대로 유지하되 적용 버전만 2.1** 이다. 2.0.0 범위는 동기화 관찰·시작 화면·버전 보존(§3~§5·§12)이다. 검증 계획도 그에 맞춰 [테스트 계획](./icloud-sync-compatibility-test-plan.md)의 단계 D 를 2.1 로 분리했다.

이 문서는 앱 시작 시 동기화 대기, 오프라인 필사, 기기 간 충돌, 외부 파일 백업·불러오기를 함께 정의한다. 동기화·버전 보존은 2.0.0, 백업·불러오기는 2.1 에 적용할 제품 방향으로 합의했으며, 실제 출시 포함은 §9의 선행 결정과 §11 검증 충족을 조건으로 한다. 문서 작성 자체는 스키마 변경이나 구현 완료를 의미하지 않는다.

관련 문서: [단일 Canvas 설계](./single-canvas-design.md), [데이터 호환성 결정](./data-compatibility-decision.md), [출시 로드맵](./release-2.0.0-roadmap.md).

**최종 합의:** 이 문서를 다음 구현 세션의 설계 기준선으로 확정한다. 구버전과 같은 가변 행을 계속 쓰는 방식을 기본안으로 삼지 않고, §12의 별도 버전 모델과 절별 초안·체크포인트 구조로 진행한다. [호환성·복구 테스트 계획](./icloud-sync-compatibility-test-plan.md)의 결과에 따라 같은 컨테이너 내 분리의 적합성을 판정한다. 검증 실패 시 저장소·컨테이너 분리 또는 출시 범위 조정을 다시 결정하며, 이를 자동 승인된 변경으로 해석하지 않는다. 시간·용량·암호화 규격 등 구현 파라미터는 실측·검토 후 기록한다.

## 1. 정책의 핵심

1. iCloud는 기기 간 동기화다. 잘못된 수정·삭제도 전파될 수 있으므로 특정 시점을 보존하는 외부 파일 백업과 역할을 구분한다.
2. 네트워크 없이도 필사한다. 로컬 저장소 준비를 앱 진입 조건으로 삼고, 원격 동기화 완료를 일반 사용의 필수 조건으로 삼지 않는다.
3. 기기에 저장됨과 iCloud 전송 상태를 구분한다. 로컬 저장 성공을 클라우드 업로드 성공으로 표시하지 않는다.
4. 충돌에서는 양쪽 필사를 보존한다. 필사 데이터의 자동 획 병합은 초기 범위에 포함하지 않는다.
5. 백업은 현재 기기에 저장된 데이터의 일관된 스냅샷이다. 아직 수신하지 못한 원격 데이터까지 포함한다고 보장하지 않는다.
6. 불러오기는 현재 데이터를 보존하며 추가한다. 백업에 없는 항목을 삭제하지 않는다.
7. 백업본을 현재 필사로 선택하는 행위는 새로운 변경이다. 과거 기록 시각과 선택한 시각을 구분한다.
8. 초기 백업 기능에는 전체 덮어쓰기 복원을 포함하지 않는다.
9. 필사 백업 생성은 유료 기능이다. 파일 검사·미리보기·불러오기는 무료이며 iCloud 동기화와 충돌 보존도 기본 기능이다.
10. 백업 기능은 **2.1 이상**에서 지원한다(2026-09-16 이관). 이전 앱에서 작성한 필사도 현재 앱에 정상 보관돼 있으면 포함한다.
11. Apple 계정이 달라도 사용자가 명시적으로 요청한 파일 불러오기는 허용한다. 계정 변경 시 기존 로컬 데이터를 자동 이전하는 문제와 구분한다.
12. 유료 백업 생성은 **기존 광고 제거 구매에 포함**한다. 기존 구매자도 같은 권한을 받으며 별도 백업 상품을 만들지 않는다.
13. **백업을 지원하는 첫 버전(2.1)부터 암호화 백업을 함께 지원**한다. 암호화 없는 백업을 먼저 내보내지 않는다. 계정 제한으로 암호화를 대체하지 않는다. 암호·키 관리와 파일 규격은 구현 설계에서 확정한다.

## 3. 앱 시작과 20초 대기

| 상황 | 목표 동작 |
|---|---|
| 기존 로컬 데이터가 있는 실행 | 로컬 저장소 준비 후 진입. 동기화 상태는 앱 사용 중에도 관찰 |
| 신규 설치·iCloud 사용 가능 | 초기 복원 안내 화면에서 대기. 처음부터 ‘먼저 시작하기’ 제공 |
| 네트워크 없음·iCloud 사용 불가 | 원인을 구분해 안내하고 로컬 사용 허용 |
| 로컬 저장소 로드 실패·마이그레이션 실패 | 오프라인 상황과 구분. 정상 저장이 불가능한 채 편집 화면에 진입시키지 않음 |

**20초는 동기화 실패를 확정하는 시간이 아니라 대기 안내를 바꾸는 기준으로 사용한다.** 20초 후 실패 표시·강제 진입을 없애고, 사용자가 기다리는 동안 관찰을 계속한다. 단순히 60초·120초로 늘리는 것은 충돌 보호가 아니다.

### 3-1. 최초 실행 흐름

1. 로컬 저장소를 준비한다. 저장소 로드 실패는 별도 복구 흐름으로 보낸다.
2. 초기 안내가 필요한 설치에서는 ‘iCloud에 저장된 필사를 확인하고 있어요’를 표시한다. 계정 확인이 지연돼도 로컬 준비 후 ‘먼저 시작하기’를 제공한다.
3. 성공한 대상 import를 관찰하고 로컬 조회·화면 준비가 끝나면 진입한다. 이미 관찰한 이벤트를 활용하며 화면 진입 후에만 구독을 시작해 이벤트를 놓치지 않는다.
4. 20초가 지나면 대기 안내를 변경한다. 계속 기다리기는 현재 화면 유지이고, 먼저 시작하기는 로컬 데이터로 진입하는 선택이다.
5. 오프라인·미로그인·계정 오류가 확인되면 원인을 안내하고 로컬 시작을 허용한다. 네트워크 상태만으로 계정 오류를 추정하지 않는다.
6. 먼저 시작했다면 앱 안에서 원격 확인 상태를 계속 안내한다. 원격 필사가 도착해도 편집 중 캔버스를 즉시 교체하지 않는다.

초기 안내 진행 여부, 대기 건너뛰기, import 성공 관찰 여부를 구분한다. 단순 `isFirstLaunch` 하나나 행 개수만으로 복원 완료를 판단하지 않는다. 기존 사용자의 앱 업데이트도 신규 설치로 취급하지 않는다. 재설치·시스템 기기 복원에서 이 상태가 복구되는 경우까지 검증한다.

이후 일반 실행은 로컬 준비 후 진입한다. 초기 대기를 건너뛴 사용자를 다음 실행마다 긴 복원 화면으로 되돌리지 않는다. 미완료 동기화는 앱 내부 상태로 보여준다.

**현재 구현과의 차이 (2026-09-17 리뷰).** 위 흐름 중 ‘먼저 시작하기’(2·4), 20초 뒤 ‘계속 기다리기’(4), 기존 사용자의 로컬 준비 후 진입은 **구현되지 않았다.** 지금은 `stillWaiting` 을 포함한 모든 결론에서 1.5초 뒤 자동으로 진입하고, 코디네이터의 첫 화면은 늘 시작 화면이다. **따라서 현재 상태는 §3-1 을 충족하지 않는다.** 선택지가 모든 출시를 막는 것은 아니지만, 2.0.0 에서 빼려면 출시 범위를 **명시적으로** 조정해야 한다. 늦은 import 와 사용자 편집이 겹칠 때 데이터가 보존된다는 근거(§4-2·§5, 테스트 계획 단계 C)가 없는 상태로 자동 진입을 안전하다고 승인하지 않으며, 버튼을 더하는 것만으로 그 보존 문제가 해결되지도 않는다.

### 3-2. 안내와 제한

안내 예시:

> 기존 필사를 불러오는 데 시간이 걸리고 있어요. 계속 기다리거나 먼저 시작할 수 있어요. 기존 필사는 나중에 나타날 수 있어요.

로컬 데이터가 비어 있다는 사실만으로 신규 사용자이거나 클라우드에도 데이터가 없다고 판단하지 않는다. 성공한 import 한 번도 모든 기기의 최신 변경 수신·내 변경 업로드 완료를 보장하지 않는다.

앱 내부 안내 예시: ‘기존 필사를 확인하고 있어요. 필사가 나중에 나타날 수 있어요.’ 확인된 오류가 생기면 해당 상태로 바꾸며 무한히 진행 중으로 표시하지 않는다.

**재설치 첫 실행의 20초 — 사용자 제기(2026-09-21)와 코드 확인.**

기존 사용자가 앱을 지우고 다시 깔면 20초로는 초기 import 가 끝나지 않는다. 그때 다음이 확인됐다.

| 질문 | 지금 코드 | 근거 |
|---|---|---|
| 20초 뒤 진입한 **열린 장**에 나중 도착분이 바로 나타나는가 | **아니다.** 열린 장은 **장을 불러올 때와 편집 환경이 바뀔 때만** 다시 읽는다. 장을 바꿨다 돌아오거나 앱을 다시 켜야 보인다 | F26(테스트 계획 §5-1)과 2026-09-21 재현 — 계정 전환으로 행 3개가 들어왔는데 열린 장은 빈 채였고 재실행하니 보였다 |
| 저장소 변경을 듣는 자리가 있는가 | **없다.** `NSPersistentStoreRemoteChange` 구독이 없고, CloudKit 이벤트(`eventChangedNotification`)는 **시작 화면의 대기 상태**에만 쓴다 | `SwiftDataContextProvider` · 코드 검색 |
| 외부 변경을 알리는 통로 | `DrawingDataRevision.bump()` 하나뿐이고 **설정의 전체 삭제만** 쓴다. 받는 쪽은 **미저장분을 버리는** 경로(`drawingDataCleared`)라 import 에 그대로 쓰면 사용자가 쓰던 획을 버린다 | `CarveDetailFeature.drawingDataRevisionChanged` |
| 20초의 범위 | 계정 조회까지 **같은 한도 안**이다. 마이그레이션은 따로 120초 | `SwiftDataContextProvider.InitialWaitLimit` |

시작 화면은 20초 뒤 「먼저 시작해도 나중에 나타날 수 있어요」 를 보이는데, **그 약속이 지켜지지 않는다** — §3-1 의 4 · 6 이 구현되지 않은 것과 같은 자리다.

**한도를 늘리는 것만으로는 증상을 미룰 뿐이다.** 순서는 이렇다.

1. **도착하면 화면이 따라오게 한다(먼저).** import 가 끝나거나 행이 늘면 열린 장을 다시 읽되 **미저장분을 버리지 않는다.** 이 세션이 편집한 절이 없으면 바로 합성하고, 편집 중이면 §3-1 의 6 대로 **바꾸지 말고** 「새 필사가 도착했어요 · 다시 읽기」 로 알린다. 초안 겹치기 규칙(②-2)이 있어 다시 읽어도 초안은 그대로다
2. **한도를 상태별로 나눈다.** 로컬이 비어 있고 계정이 있는 **첫 실행 · 재설치**만 늘린다(마이그레이션과 같은 120초까지 검토). 로컬에 이미 데이터가 있으면 기다릴 이유가 없다 — 보여 줄 것이 이미 있다. 늘리는 동안에는 **진행(받은 행 수)** 과 **「먼저 시작하기」** 를 함께 둔다(§3-1 의 2 · 4)
3. **숫자는 재고 정한다.** 실제 계정 규모(실사용 271행 · 잉크 평균 15.3 KB · 최대 111 KB)로 **첫 행 도착**과 **완료**까지를 재고 나서 한도를 정한다. 관측 도구는 있다(2초 관측기 · `probe.sh`)
4. 필사 화면에 **받아오는 중 띠**를 둔다 — 빈 장을 데이터 유실로 읽지 않게. 첫 실행에 쓴 필기는 ②-2 규칙상 초안으로만 남고 저장소를 덮지 않으므로(F27 막음) 늦게 온 원본을 가리지는 않는다

**나중 변경(F8)은 별개다** — 켜 둔 앱은 다른 기기의 변경을 재실행 전까지 가져오지 않았고 푸시 권한(`aps-environment`)이 없다. 첫 실행의 import 는 이미 진행 중이므로 1번으로 해결되지만, 그 뒤의 원격 변경까지 바로 받으려면 푸시가 필요하다.

초기 import는 설치 후 첫 실행에서 예약되지만 실제 실행 시점은 시스템이 결정한다. 앱에서 동기화 시간을 강제 지정하는 방식으로 해결하지 않는다. [Apple 동기화 설명](https://developer.apple.com/documentation/technotes/tn3163-understanding-the-synchronization-of-nspersistentcloudkitcontainer), [동기화 시점 제약](https://developer.apple.com/documentation/technotes/tn3164-debugging-the-synchronization-of-nspersistentcloudkitcontainer)

‘먼저 시작하기’의 편집 안전성은 §5의 버전 보존과 함께 구현·검증한다. 시작 화면 수정만으로 충돌 보호가 완료됐다고 간주하지 않는다.

`migration` 경로는 일반 동기화 UX 변경에 그대로 포함하지 않는다. 현재 V1 fallback과 재실행 요구는 별도 검증해야 하며, 타임아웃 뒤 현재 앱의 저장 모델로 안전하게 편집 가능한지부터 확인한다.

**2026-09-17 확인 — 안전하지 않았다(테스트 계획 MIG-F1).** V1 fallback 상태의 저장소(V1 전용 컨테이너)에서는 필사 조회가 비고, 저장은 오류 없이 끝나지만 다시 읽히지 않는다. 그런데도 계정 없음 · 계정 확인 실패 · import 실패 · 시간 초과가 일반 모드와 같은 결론으로 끝나 편집 화면에 들어갔다. 이제 `migration` 모드는 결론이 무엇이든 편집 화면에 들어가지 않고 재실행을 요구한다(import 성공이 아니면 "완료" 라고 하지 않는다). 진입 판정은 `LaunchRoute` 로 옮겨 단위 테스트로 고정했다.

## 4. 저장·동기화 상태와 화면 반영

### 4-1. 상태는 서로 분리한다

- 로컬 저장: 저장 중 / 저장됨 / 저장 실패·재시도 필요.
- 동기화: 상태 확인 중 / 작업 진행 중 / 최근 import·export 성공 시각 / 지연 또는 오류 / 계정 조치 필요.
- 충돌: 없음 / 비교·선택이 필요한 버전 있음.

단순 이벤트만으로 특정 필사가 서버에 저장됐거나 모든 기기에 전달됐다고 표시하지 않는다. 정확한 미전송 건수를 구현하지 않았다면 숫자를 추정해 보여주지 않는다. 네트워크 연결 상태는 참고 정보이며 실제 동기화 성공의 증거가 아니다.

이벤트 관찰은 앱 수명 동안 유지하고 성공·오류 및 대상 저장소를 구분한다. 실제 구성과 동일한 CloudKit 컨테이너의 계정 상태를 조회한다. 계정 조회 지연도 앱 진입 정책에서 다룬다.

### 4-2. 편집 중 원격 변경

- 현재 캔버스를 원격 데이터로 즉시 교체하지 않는다.
- 편집 기준 버전과 로컬 변경을 보존한 뒤 원격 버전과 비교한다.
- 미저장 편집·저장 중 작업이 없으면 안전한 시점에 갱신한다.
- 서로 갈라진 버전이면 두 버전을 보존하고 비교·선택할 수 있게 한다.
- 로컬 저장 실패를 동기화 지연 문구로 숨기지 않는다. 메모리 큐 보존만으로 앱 종료 후 복구를 보장하지 않는다.

> **실측 (2026-09-17, 시뮬레이터 · [테스트 계획](./icloud-sync-compatibility-test-plan.md) CK-A4b · CK-A4c):** 켜 둔 두 기기가 서로 모르고 같은 절을 고치면, 나중에 올린 쪽이 절 필기 전체를 덮어써 먼저 쓴 필기가 **오류도 안내도 없이** 사라졌다. 2.0.0 끼리도 같았다. 실행 중인 앱은 다른 기기 변경을 재실행 전까지 가져오지 않았으므로(테스트 계획 F8 — 두 앱에 푸시 권한이 없는 것이 원인으로 추정되나 미확인) 이 상황은 드물지 않을 것으로 본다. 위 원칙과 §5 의 버전 보존이 막으려던 유실이 현재 구현에서 재현된 것이다.

## 5. 필사 버전 보존 — 구현 설계 제안

### 5-1. 불변 버전

동일 행의 현재 내용만 반복 교체하는 구조에서, 확정된 필사를 별도 불변 버전으로 추가하는 구조로 전환한다. 이는 구현 전 상세 스키마·마이그레이션 검토가 필요한 제안이다.

| 개념 필드 | 의미 |
|---|---|
| 논리 버전 ID | 재시도·백업 왕복에도 유지되는 버전 식별자. SwiftData 내부 ID와 구분 |
| 절 식별자 | 번역본·성경 권·장·절을 구분. 기존 번역본 미상 데이터 처리 필요 |
| 부모 버전 ID 목록 | 편집 기반과 분기·충돌 해결의 계보. 단순 정수 증가나 시각만으로 대체하지 않음 |
| 필사 payload | drawing·좌표 형식·레이아웃 메타데이터를 하나의 버전으로 해석 |
| 원래 기록 시각 | 사용자가 필사한 시각. 정렬·표시용이며 인과관계 증명이 아님 |
| 작업 종류 | 편집·지우기·복원 선택 등 변경 의도 |
| 가져오기 출처 | 백업 식별자·원본 버전 ID 등 중복 판정과 추적 정보 |

예: A에서 B와 C가 각각 만들어지면 둘 다 보존한다. 사용자가 B를 선택해 해결하면 B·C를 인지한 새 결과 D를 만든다. 단일 가변 `currentVersionID`의 마지막 값만으로 충돌이 해결됐다고 판단하지 않는다. 도착 순서가 다른 기기에서도 같은 계보로 미해결 분기를 찾을 수 있어야 한다.

부모보다 자식이 먼저 수신되는 경우도 허용한다. 잠시 부모가 없다는 이유로 손상으로 확정하거나 버전을 제거하지 않는다. 동일 논리 ID인데 payload가 다르면 조용히 하나를 버리지 않고 무결성 오류로 다룬다.

### 5-2. 저장 주기와 보관

모든 획마다 전체 스냅샷을 영구 보존하면 용량·전송 비용이 증가한다. 로컬 초안은 빈번하게 내구성 있게 저장하고, 확정 버전 생성은 편집 구간·장 전환 등으로 묶는 방식을 검토한다. 구체적인 주기와 초안 복구 계약은 미결정이다.

**확정 버전으로 남기기 전 가변 초안 구간은 보호 공백이 될 수 있다.** 클라우드가 덮을 수 있는 동일 행에만 초안을 두지 않는다. “보존을 보장하는 편집 단위”를 먼저 정의하고 종료·크래시·저장 실패를 검증한다.

지우기도 빈 결과를 가진 새 변경으로 남긴다. 사용자에게 보이는 기록 숨김, 현재 필사 지우기, 이력 영구 삭제는 서로 다른 기능이다.

이력 자동 정리는 초기에는 보수적으로 접근한다. 오래 오프라인인 기기와 외부 백업은 과거 버전을 다시 가져올 수 있다. 모든 기기의 수신 완료를 증명하기 어려우므로 보관 기간만으로 안전한 삭제를 단정하지 않는다. 미해결 분기·필요한 조상·삭제 표식의 정리 규칙은 별도 결정한다.

## 6. 외부 파일 백업 〈2.1 범위〉

### 6-1. 생성 흐름

1. 진행 중인 편집과 저장 큐를 로컬에 반영한다. 실패하면 백업 성공으로 진행하지 않는다.
2. 일관된 읽기 스냅샷을 확보한다. 원격 import가 동시에 진행돼도 payload와 메타데이터가 서로 다른 시점에서 섞이지 않아야 한다.
3. 임시 위치에 백업을 생성하고 건수·참조·무결성을 검사한다.
4. 검사가 끝난 파일을 외부 위치로 내보낸다. 사용자의 취소와 파일 쓰기 실패를 성공과 구분한다.

네트워크가 없어도 생성 가능하다. iCloud Drive 같은 외부 파일 제공자에 저장할 경우, 앱의 파일 내보내기 성공과 그 제공자의 원격 업로드 완료는 별개다.

안내 예시:

> 이 기기에 저장된 필사를 백업합니다. 아직 동기화되지 않은 다른 기기의 필사는 포함되지 않을 수 있어요.

### 6-2. 파일 형식

SQLite와 CloudKit 내부 동기화 메타데이터를 복사·교체하지 않고 앱 전용 이식 가능한 형식을 사용한다. 확장자와 압축 방식은 미결정이다.

필수 후보:

- manifest: 파일 형식 버전, 생성 앱 버전, 생성 시각, 백업 ID, 포함 범위·건수.
- 논리 버전 ID·부모 참조·절 식별자·원래 기록 시각.
- drawing 원본, 좌표 형식 버전, 레이아웃 메타데이터.
- 항목별 크기·체크섬 및 필요한 참조 정보. 체크섬은 손상 검출용이며 작성자 인증 수단은 아니다.

알 수 없는 새 형식이나 해석 불가능한 좌표 버전은 조용히 변환·폐기하지 않는다. 지원 가능 범위를 확인하고 원본 파일을 보존한 채 안내한다. 외부 바이너리를 디코딩할 때 파일·항목 크기, 압축 해제 용량, 경로 이탈 등도 제한한다.

### 6-3. 2.0.0 지원 범위와 버전

사용자 기능명은 **필사 백업**으로 한다. 초기 대상은 `BibleDrawing`의 현재·보관 필사와 복구에 필요한 버전 정보다. 버전 정보를 별도 엔티티로 구현하면 그 정보도 포함해야 하며, 테이블 하나만 내보내는 것으로 범위를 고정하지 않는다.

`FavoriteVerse`의 독립 스냅샷, 설정·위젯 구성은 포함하지 않는다. 따라서 즐겨찾기에만 남은 필사는 이 백업의 복구 대상이 아님을 범위 안내에 명시한다. 구매 권한·계정 토큰·CloudKit 내부 상태도 제외한다.

| 버전 | 역할·정책 |
|---|---|
| 앱 버전 | **2.1 이상**에서 백업 생성·불러오기 지원(2026-09-16 이관). 2.0.0 을 포함한 이전 앱 자체에는 기능 없음 |
| 저장소 스키마 | 현재 `DrawingSchemaV5`는 `DrawingSchemaV4.BibleDrawing`을 그대로 사용. 독립된 `BibleDrawingV5`로 간주하지 않음 |
| 백업 형식 | 독립적인 `formatVersion = 1`부터 시작. 앱 버전·스키마 버전과 분리 |
| 필사 좌표 형식 | `drawingVersion`과 레이아웃 메타데이터를 원본과 함께 보존. 내보내기만으로 좌표 형식을 임의 승격하지 않음 |

이전 앱에서 작성한 필사도 현재 앱에 정상적으로 보관돼 있으면 백업한다. ‘이전 앱의 백업 기능 미지원’과 ‘이전 필사 제외’를 혼동하지 않는다. 구형 좌표 데이터의 왕복 복구 검증은 필수다.

### 6-4. 유료 권한

| 기능 | 권한 |
|---|---|
| 새 백업 파일 생성 | 유료 |
| 파일 검사·미리보기·불러오기 | 무료 |
| iCloud 동기화·충돌 보존 | 기본 기능 |

새 기기의 구매 복원 실패나 계정 변경 때문에 이미 만든 파일의 복구를 막지 않는다. 구매를 확인하기 위한 네트워크 요청을 무료 불러오기의 진입 조건으로 삼지 않는다. 유료 생성의 오프라인 권한 처리는 기존 결제 구조와 맞춰 설계한다.

**2026-09-16 결정:** 기존 광고 제거 구매에 백업 생성 권한을 포함한다. 기존 구매자도 추가 결제 없이 사용한다. 별도 상품이나 새 구독은 도입하지 않는다. 파일 검사·불러오기는 구매 여부와 무관하게 무료다. 구매 상태와 기능 권한의 매핑을 명시하고, 기존 광고 제거 상품 설명·앱 내 안내가 실제 제공 범위와 맞도록 갱신한다.

### 6-5. 암호화 지원

**2026-09-16 결정:** 백업을 지원하는 첫 버전(2.1)부터 암호화 백업을 함께 지원한다. 권장 구현은 Apple 계정에 묶이지 않는 사용자 암호 기반 방식이다. 새 기기와 다른 계정에서도 파일과 암호로 복구할 수 있어야 한다.

구체적인 암호화·암호 기반 키 유도 규격과 큰 파일 처리 방식은 보안 검토 후 확정한다. 검증된 구현을 사용하고 직접 암호 알고리즘을 만들지 않는다. 암호·복호화 키·필사 평문을 로그에 남기지 않는다. 암호화 전후 임시 평문 파일의 수명과 앱 중단 시 정리도 검증한다.

미결정 세부 사항: 암호화를 항상 적용할지 선택 사항으로 둘지, 암호 저장 편의 기능을 제공할지. **초기 권장안은 내보내기 시 암호를 설정하는 기본 암호화 방식**이며, Carve가 암호를 대신 보관하거나 분실한 암호를 복구한다고 약속하지 않는다. 잘못된 암호·변조·손상 파일은 현재 저장소를 변경하기 전에 거부한다.

## 7. 불러오기 〈2.1 범위〉

### 7-1. 기본 적용 규칙

| 입력 상황 | 처리 |
|---|---|
| 현재 없는 필사 | 추가. 이미 다른 현재 필사가 있는지 적용 시점에도 재평가 |
| 같은 논리 버전·같은 내용 | 건너뛰기 |
| 같은 절의 다른 버전 | 보관본으로 추가하고 현재 필사는 유지 |
| 백업에 없는 절 | 현재 데이터 유지 |
| 사용자가 백업본을 현재 필사로 선택 | 기존 내용 보존 후 새로운 선택·복원 변경 기록 |
| 같은 파일 반복 가져오기 | 논리 ID와 가져오기 기록으로 재시도해도 중복되지 않게 처리 |
| 동일 논리 ID·다른 내용 | 무결성 문제로 격리·안내. 묵시적 덮어쓰기 금지 |

가져온 행 전체에 `isPresent = true`와 현재 `updateDate`를 넣지 않는다. 원래 필사 시각, 가져온 시각, 현재 필사로 선택한 변경을 분리한다.

안내 예시:

> 새 필사 120개 · 동일한 필사 80개 · 현재 필사와 다른 버전 15개. 현재 필사는 유지되며, 다른 버전은 필사 기록에 추가됩니다.

미리보기 수치는 검사 시점의 값이다. 그 뒤 동기화로 저장소가 바뀔 수 있으므로 적용 시점에도 검증하고 실제 결과를 보고한다.

### 7-2. 검증·중단·재시도

1. 파일 접근·다운로드가 필요한 경우 준비 상태부터 확인한다.
2. 앱의 작업 영역에서 형식·버전·참조·payload를 검증한다. 손상된 데이터를 현재 저장소에 먼저 넣고 나중에 검증하지 않는다.
3. 추가·중복·다른 버전·지원 불가 항목을 미리 보여준다.
4. 사용자 적용 요청 후 저장한다. 작업 ID와 진행 상태를 내구성 있게 보관해 종료 후 재시도한다.
5. 실제 적용·건너뜀·실패 결과를 표시한다. 로컬 반영과 iCloud 전송은 구분한다.

작은 백업의 단일 트랜잭션과 큰 백업의 배치 적용 중 구현 전략을 선택해야 한다. 배치 적용이라면 취소·실패 시 이미 반영된 범위와 재시도 동작을 명시한다. 로컬 전체 원자성을 구현하더라도 다른 기기에 한꺼번에 보이는 CloudKit 원자성까지 보장하지 않는다.

적용된 데이터는 일반 데이터와 같이 iCloud 동기화 대상이다. 일단 업로드된 항목을 단순 로컬 rollback만으로 모든 기기에서 되돌릴 수 있다고 안내하지 않는다.

### 7-3. 동기화와 함께 동작

불러오는 동안 동기화를 잠시 중지하는 방식에 안전성을 의존하지 않는다. 원격 변경이 전·중·후 어느 때 도착해도 두 버전을 보존한다.

두 기기가 오프라인에서 같은 파일을 가져오면 각각 중복 검사를 통과할 수 있다. 논리 ID를 유지하는 것만으로 물리 행 중복이 방지되는 것은 아니므로, 수신 후 동일 버전을 하나로 취급하는 조회·정규화 규칙도 필요하다. 파괴적인 중복 행 삭제는 참조 보존 검증 후 별도로 다룬다.

### 7-4. Apple 계정과 파일 소유

다른 Apple 계정에서 만든 백업도 사용자가 파일을 선택해 요청하면 불러올 수 있다. iCloud 미로그인 상태도 로컬 파일 불러오기를 허용한다. 계정 ID 일치 검사를 파일 복구 조건으로 삼지 않는다.

적용 전 안내: ‘불러온 필사는 이 기기에 저장되며, 현재 연결된 iCloud 계정으로 동기화될 수 있어요.’

이는 계정 변경만으로 기존 로컬 필사를 새 계정에 자동 전송하는 정책에 대한 허용이 아니다. 자동 전송·저장소 분리의 실제 동작은 별도 검증한다. 개인정보 보호가 필요하면 파일 암호화로 다루며, manifest의 계정 문자열 비교를 암호화나 접근 통제로 간주하지 않는다.

## 9. 구현 시 확인할 사항과 2.0.0 착수 기준

제품 방향은 합의했으므로 시작 화면·동기화 상태 정정과 백업 파일 계약 설계를 시작할 수 있다. 다만 아래 선행 항목을 해결하지 않은 채 새 저장 스키마와 결제 상품을 확정하지 않는다. 세부 구현 선택은 조사·실측으로 좁히며 모두 사용자에게 다시 물을 필요는 없다.

### 9-1. 구현 전 검증·상세화

| 항목 | 필요한 결정 | 시점 |
|---|---|---|
| 구버전 앱과 legacy 전환 | 구버전이 같은 필사를 수정할 때 보존·수용 범위, 여러 기기에서 일관된 전환 ID | 스키마 확정 전. 기존 호환성 문서와 함께 조사 |
| 초안·확정 버전 | 어떤 시점의 필사까지 종료 후 보존하는지, 버전 생성 주기·용량 상한 대응 | 저장 구현 전. 내구성 실험과 성능 측정으로 확정 |
| 계정 전환 시 로컬 데이터 | 전환 뒤 기존 로컬 필사가 **어느 계정에 귀속되는지**, 새 계정으로의 묵시적 전송 방지 방법과 로컬 보존 방식 | 동기화 저장소 설계·출시 전. 실제 동작 검증 필요(전용 계정 두 개) |
| 로컬 저장소 준비 실패·V1 폴백 상태의 편집 진입 | §3 표 4행(정상 저장이 불가능한 채 편집 화면에 진입시키지 않음)을 어떻게 구현할지. V1 폴백은 크래시가 아니라 **조용한 초기화**로 진입한다(테스트 계획 F7) | 출시 전. 계정 없이 시험 가능 — 단계 L·DOWN-L2 와 같은 방법 |
| 백업 암호화 세부 | 지원 자체는 확정(2.1). 기본 적용 여부·암호 관리·파일 규격 확정 | 2.1 파일 형식 구현 전 |

유료 상품 구성은 기존 광고 제거 구매에 포함하는 것으로 결정됐다. 계정 제한 없는 불러오기와 암호화 지원도 확정이며, **적용 버전은 2.1** 이다.

### 9-2. 구현 중 확정할 세부 사항

| 결정 | 권장 출발점 |
|---|---|
| 선택 백업 지원 | 첫 버전은 전체 필사 백업 우선. 일부 백업은 manifest에 범위를 명시 |

**출시 조건:** 아래 검증 중 **2.0.0 범위(백업·불러오기 제외)** 를 충족하면 2.0.0 적용 방향으로 진행한다. 충돌 보존과 구버전 호환성의 안전성이 확인되지 않으면 시작 화면·동기화 상태 개선만 분리해 출시할 수 있으나, **충돌 보호까지 완료했다고 안내하지 않는다.** 백업·불러오기는 2.1 이므로 2.0.0 안내에 넣지 않는다. 범위 이월은 사용자와 명시적으로 결정한다.

## 10. 구현 순서와 경계

3. **편집·원격 변경 보호:** Repository 버전 저장과 안전한 캔버스 갱신, 충돌 기록 UI.
4. **실기기 통합 검증 후 2.0.0 출시 범위 확정.**

이후 **2.1** 에서:

5. **백업 내보내기:** 일관된 스냅샷·파일 검증·외부 쓰기 결과 처리. 파괴적 불러오기보다 독립적으로 먼저 제공 가능.
6. **불러오기:** 사전 검사·미리보기·중복 방지·재시도·동기화 동시 도착 처리.

우리 룰 기준:

- SwiftData 모델 접근은 Domain의 Repository/Client 안에 둔다.
- Feature는 저장·동기화·충돌 상태와 도메인 명령만 다룬다.
- 파일 I/O와 상태 관찰은 Dependency + Effect를 통해 수행한다.
- 스키마·의존성·빌드 설정은 이 문서 작성으로 변경하지 않는다.
- 필요한 새 스키마는 개발 환경 검증과 Production 승격 절차를 별도로 거친다.

현재 검증 상태: **정책과 코드 경로를 검토했으며, 이 문서의 목표 동작은 구현·실기기 검증 전이다.**

## 12. 구버전 호환성과 저장 단위 설계 기준선 (2026-09-16)

아래는 현행 코드와 출시 커밋을 대조해 확정한 **구현 기준선**이다. 저장소 분리의 적합성은 테스트 계획으로 판정하고, 시간 파라미터는 실측한다. 새 모델·저장 주기 자체가 구현·검증 완료됐다는 뜻은 아니다.

### 12-1. 코드로 재확인한 사실

- 출시본으로 기록된 `49f2dc27`의 `DrawingDatabase.updateDrawings`·`updateDrawing`은 기존 행의 `lineData`·`updateDate`를 바꾸며 `drawingVersion`을 수정하지 않는다. 스키마는 V3이고 새 좌표 메타데이터·행 UUID를 모른다.
- 따라서 새 좌표 데이터와 구버전이 같은 가변 행을 공유하면 좌표 라벨과 실제 데이터가 어긋날 수 있다. 새 필드 추가만으로 해결되지 않는다.
- 현행 단일 Canvas는 마지막 변경 후 약 0.3초 trailing debounce로 스냅샷을 보고한다. 다음 도구 사용이 시작되면 보고를 연기할 수 있다.
- `ChapterCanvasSaveFeature`는 준비된 절별 mutation을 한 장의 batch로 묶어 저장을 직렬화한다. 실패 시 큐는 메모리에 남는다.
- 비활성화 시 `CarveNavigationView` → `CarveDetailFeature` → `.flushPending`으로 이어지며, 이 액션은 준비된 저장 큐를 처리한다. 해당 경로 자체에는 컨트롤러의 `hasUnreportedChange`를 강제 수집하는 명령이 없다. 재합성 시 별도 수집 경로는 있으나 비활성화 순간의 마지막 획 보장으로 대신할 수 없다.

참조: [출시본·호환성 조사](./data-compatibility-decision.md), [현재 저장 처리](../Feature/CarveFeature/Sources/Presentation/Drawing/ChapterCanvas/ChapterCanvasSaveFeature.swift), [캔버스 변경 보고](../Feature/CarveFeature/Sources/Presentation/Drawing/ChapterCanvas/ChapterCanvasController.swift), [비활성화 처리](../Feature/CarveFeature/Sources/Presentation/Carve/CarveDetail/CarveDetailFeature.swift).

### 12-2. 구버전 데이터 수용과 새 버전 저장을 분리

**2.0.0 필사 원본은 별도 불변 버전 모델로 저장하고, 기존 `BibleDrawing`은 legacy 데이터 수신·보존 경로로 둔다. 2.0.0 결과를 구버전 행에 자동으로 다시 쓰는 양방향 호환은 제공하지 않는다.** 새 엔티티 이름·스키마 번호는 상세 설계에서 정한다.

| 데이터 방향 | 추천 동작 |
|---|---|
| 기존 필사 → 2.0.0 | 원본·좌표 정보를 보존하며 새 버전 모델로 수용 |
| 구버전에서 이후 편집 → 2.0.0 | 관찰된 새 내용을 별도 legacy 후보로 보존. 새 앱의 현재 필사를 자동 교체하지 않음 |
| 2.0.0 편집 → 2.0.0 | 새 버전 모델끼리 동기화하고 분기·선택 규칙 적용 |
| 2.0.0 편집 → 1.3.0 | 표시·편집 동기화를 지원하지 않음. 모든 기기의 업데이트 필요 안내 |
| 구버전 삭제 → 2.0.0 | 이미 보존한 새 버전을 자동 삭제하지 않음 |

이 방식의 대가는 **혼재 버전에서 양방향 필사 동기화를 포기하는 것**이다. 이 범위를 설계 기준선에 포함하며, 출시 안내에 모든 iPad의 업데이트가 필요함을 명시한다. 기존 필사를 지우거나 구버전 앱을 원격 차단한다는 의미가 아니다.

V4·V5 로컬 DB를 구버전 바이너리로 직접 여는 다운그레이드와, 다른 iPad의 V3 저장소가 CloudKit 변경을 수신하는 상황은 다르다. 새 필드가 있다는 이유만으로 구버전이 반드시 크래시한다고 가정하지 않는다. 디코딩·표시·저장까지 진행되면서 의미가 어긋나는 경우도 시험한다. 크래시·동기화 중단을 구버전 쓰기 차단의 성공으로 판정하지 않는다.

이 분리는 **동기화 충돌 보호**를 위한 설계다. 과거 N-canvas 필사의 파일 백업 자체에 필수인 것은 아니다. 백업은 기존 `drawingVersion`과 원본·메타데이터를 보존해 같은 파일 형식에 담고 왕복 검증하면 된다. 스키마 V3와 필사 좌표 형식 3을 혼동하지 않는다.

별도 엔티티라면 구버전의 일반 필사 갱신 대상에서 새 원본을 분리할 수 있지만, CloudKit의 미지 엔티티 처리·기존 앱의 전체 삭제 범위까지 안전하다고 단정할 수는 없다. 같은 테스트 계정에서 구·신 버전 왕복과 삭제 범위를 검증한다. 새 레코드 타입 운영 승격도 필요하다.

legacy 수용의 중복 방지는 기존 출처 식별 정보와 원본 내용·좌표 메타데이터의 정규화된 fingerprint를 조합하는 방안을 검토한다. business ID만으로 서로 다른 원본을 합치지 않는다. 안정적인 출처 ID를 얻는 방법과 정규화 규칙을 먼저 검증한다. fingerprint는 원본 내용 식별용이며 편집 인과관계나 시각을 증명하지 않는다.

구버전이 동일 가변 행을 여러 번 덮은 사이 새 앱이 중간 상태를 수신하지 못했다면 그 중간 편집까지 복원할 수 없다. 보장 범위는 **2.0.0이 실제로 수용·보존한 버전과 2.0.0 자체 편집**이다. 이미 좌표 라벨과 내용이 어긋난 데이터는 원본을 남기고 별도 복구 대상으로 다룬다.

### 12-3. 절별 로컬 초안 + 절별 불변 체크포인트

데이터 단위는 **절별**로 유지한다. 장 전체 drawing을 하나의 충돌 단위로 만들지 않는다. 장 batch는 로컬 저장 효율을 위한 묶음이며, 다른 기기에 한꺼번에 도착하는 단위가 아니다.

| 단계 | 추천 저장 단위·시점 |
|---|---|
| 로컬 초안 | 변경된 절의 최신 drawing·메타데이터·기준 버전. 현행 약 0.3초 안정화 뒤 내구성 있는 로컬 저장 |
| 연속 편집 중 초안 | trailing debounce만으로 무한 연기되지 않게 최대 대기 후보 2초. 진행 중 도구를 완료 처리하지 않는 별도 캡처 경로 검증 |
| 동기화할 확정 버전 | 변경된 절만 불변 버전 생성. 초기 실험값은 편집 중단 10초 또는 첫 미확정 변경 후 30초 중 먼저 도달한 시점 |
| 경계 이벤트 | 장 전환·앱 비활성화·백업 시작·지우기·기록 복원 전에 최신 캔버스 수집 → 초안 저장 → 확정 버전 생성 |

0.3초는 현행 구현값이고 **2초·10초·30초는 새 실험의 출발값**이다. 저장 성공 시한이나 허용 유실량으로 보장하지 않는다. 긴 획·지우개·올가미·Undo/Redo에서 일관된 스냅샷을 만들 수 있는지, iPad의 인코딩 비용·필기 지연·용량을 측정한 뒤 확정한다.

로컬 초안은 CloudKit이 덮어쓸 수 없는 비동기화 저장 영역에 둔다. 초안 저장 후에만 ‘기기에 저장됨’으로 표시한다. 앱 종료 후 초안이 남아 있으면 원래 기준 버전에 연결해 복구하고, 그 사이 도착한 원격 필사와 별도 분기로 보존한다.

초안과 CloudKit용 저장소 사이의 원자성을 가정하지 않는다. 확정할 버전 ID와 payload를 먼저 내구성 있게 기록하고, 같은 ID로 재시도 가능한 방식으로 버전 저장을 수행한다. 버전 로컬 커밋 확인 후에만 해당 초안을 완료 처리한다. 두 저장 사이에 종료돼도 중복·유실이 없어야 한다. 네트워크 export 완료를 기다렸다가 초안을 정리하는 방식은 아니다.

**초안을 지우는 근거 (2026-09-18, 9차 리뷰 — F29 결정).** 위의 "버전 로컬 커밋 확인 후 초안 완료" 는 **확정 흐름(③)이 별도의 내구성 있는 복구 사본을 남긴다는 전제**다. 순서는 **복구 사본 저장 → 버전 로컬 커밋 → 그 초안 revision 정리**다(C2 · C11 복구 사본 — 2.0.0 에서 자동 해제하지 않는다). 기존 `BibleDrawing` 만 쓰는 ② 중간 상태에는 적용하지 않는다. 로컬 저장은 보존이 아니다 — 전송 전에 계정이 바뀌면 미러링이 그 행을 지우고 원래 계정으로 돌아와도 되살리지 않았다(ACC-1 F29).

- ② 는 **마지막 로컬 사본을 남긴다.** 저장소 저장을 마친 초안도, 저장소와 같은 내용이라 겹치지 않는 다른 세션의 초안도 지우지 않는다.
- 초안의 **역할이 끝나는 것**(그 revision 을 다시 겹치지 않음)과 **복구 가능성을 없애는 것**(파일 삭제)을 나눈다. 같은 세션 · 절은 새 revision 이 덮는 것만 허용한다.
- 역할이 끝났다는 사실은 **초안에 영속 표식으로 남긴다**(저장소 저장과 초안 저장을 둘 다 마친 revision). 메모리에만 두면 다음 세션이 "빈 절에 X 를 써서 저장 → 그 절을 지움" 을 기준 지문만으로는 가리지 못해 지운 필기를 되살린다. 표식이 있어도 그 행이 저장소에서 사라졌으면(전송 전 계정 전환 · 다른 기기의 삭제) 되살릴 수 있게 보이되 보이기만 한다.
- "확정 뒤 시작한 export 성공" 도 정리 근거가 아니다 — `NSPersistentCloudKitContainer.Event` 는 작업 성공과 저장소 식별만 주고, 어떤 레코드 · revision 이 올라갔는지는 주지 않는다.

비활성화 시에는 준비된 mutation 큐뿐 아니라 컨트롤러의 미보고 변경과 변환 중 작업까지 수집·완료시키는 경계가 필요하다. 강제 종료는 마지막 callback을 보장하지 않으므로 정상 편집 중 초안 저장이 기본 보호다. 디스크 커밋 전 마지막 변경까지 저장됐다고 약속하지 않는다.

같은 내용을 반복 저장하지 않고, UI 기록은 편집 구간별로 묶어 표시한다. 내부 체크포인트를 전부 기록 목록의 별도 카드로 노출할 필요는 없다. **UI 묶음과 실제 이력 삭제는 별개**이며 자동 영구 정리는 초기 범위에서 보류하는 것을 추천한다. 체크포인트가 너무 커지면 보존 보장을 조용히 줄이지 말고 저장 주기·압축·데이터 표현을 재평가한다.

### 12-4. 구현 전 검증 범위

1. 1.3.0 코드와 2.0.0 후보를 같은 개발 CloudKit 데이터로 연결해 새 엔티티 수신·legacy 편집·삭제의 영향을 확인한다. 출시 앱의 운영 데이터에는 시험하지 않는다.
2. 초안 커밋 전·후, 확정 버전 기록 전·후에 종료를 주입해 재시도와 복구를 확인한다.
3. 마지막 변경 후 0.3초 이내 비활성화, 쉬지 않는 연속 필기, 긴 획, 지우개·올가미·Undo/Redo에서 누락과 표시 변경을 확인한다.
4. 장시간 필사로 절별 blob 크기·체크포인트 증가량·피크 메모리·저장 지연을 측정해 주기를 확정한다.

이번 조사는 코드·문서 검토이며 위 검증은 아직 실행하지 않았다. 최소 버전 안내나 로컬 단위 테스트만으로 구버전 CloudKit 호환성 검증을 대체하지 않는다.

실행 순서·fixture·통과 기준·실패 분기·결과 양식은 [호환성·복구 테스트 계획](./icloud-sync-compatibility-test-plan.md)을 따른다. 다음 세션에서는 이 계획의 준비 확인과 최소 호환성 실험부터 시작하고, 전체 기능 구현 후에 호환성을 처음 확인하는 순서로 진행하지 않는다.

중"(`storeState = .sending`)을 달아 두고 저장소 저장이 끝나면 "들어감"(`.stored`)으로 바꾼다 — 표식을 바꾸기 전에 끝나도 다음 실행은 저장 완료를 확정된 사실로 보지 않는다. **불러올 때 초안 복구**(`VerseDraftRecoveryRule`): 지금 세션의 초안은 겹치고(저장소에 넣은 revision 은 빼고), 다른 세션의 초안은 근거가 막히지 않고(계정 · K) 기준 지문이 지금 저장소 내용과 같을 때만 겹친다 · 같은 내용이면 겹치지 않되 지우지 않음. 저장소로 보낸 초안은 **그 행의 지금 내용**과 견준다 — 초안과 같으면 정리 대상 · 행이 사라졌으면 그 절이 비었거나 기준 그대로일 때 보이기만(기존 필기를 고친 F29 포함 — 기준 행이 함께 사라진다) · 편집 전 내용 그대로면 보통 규칙 · **내가 앞서 넣은 내용**(`sentFingerprints` — 표식을 남길 때 **실제로 넣은 내용**으로 적는다. 초안 파일이 그 사이 더 새 revision 이어도 남기고, 다른 세션이 이어받으면 그 기록도 물려받는다)으로 돌아왔으면 그 뒤 revision 이 저장소에 닿지 않은 것이므로 근거만 보고 잇는다(ACC-1 2차 ⑪) · 그 뒤로 바뀌었으면 보존만(지우기 · 복원 뒤 되살아나지 않는다. 보내는 중이었으면 **저장 완료가 불확실한 초안**으로 따로 센다) · 나머지는 보존만. **이어 쓰기는 둘로 나눈다** — 근거가 유효하고 지금 세션도 소유 근거가 있으면 지금 세션으로 이어 쓰고(원 초안은 새 초안을 쓴 뒤, 보였던 그 revision 일 때만 지운다), 그 밖(보존만 · 확인 대기 초안)은 **보이기만** 한다: 그 절의 편집은 원 초안의 출처(계정 근거 · K · 소유 근거 · 기준)를 잇고, 지금 세션이 유효해도 저장소에 쓰지 않으며, 원 초안은 출처가 그대로 이어질 때만 대신한다(④ 의 명시적 가져오기 전까지 — 한 획을 더한 것은 가져오기 동의가 아니다). 겹친 초안은 **저장소에 자동으로 쓰지 않는다.** **확인 전(`acct-unverified`) 묶음의 초안**은 그때 참고하던 계정(힌트)이 지금 확인된 계정과 같을 때 함께 읽어 **보이기만** 한다 — 묶음 · 출처 · 저장소는 그대로다(사용자 결정 2026-09-21, ACC-1 2차 ④). 힌트가 다르면 다른 계정의 필기일 수 있어 읽지 않는다. **초안을 읽지 못하면**(그 장의 초안 파일 하나라도 읽지 · 풀지 못함, 초안 폴더를 끝까지 읽지 못함 — 묶음 폴더가 없을 때만 빈 목록이다 — 초안을 읽은 삭제 세대가 조회 환경과 다를 때 포함) 조회 실패처럼 입력을 막고 "이 기기에 남은 필기를 불러오지 못했어요 · 다시 시도" 를 보인다 — 삭제 세대를 읽지 못했으면 다시 시도할 때 다시 읽는다. 마지막으로 알던 내용으로 여는 재조회 출구는 같은 세션의 저장소 재조회 실패에만 쓴다(초안 읽기 실패 · 세션을 새로 연 뒤에는 막는다). **세션 종료**는 ① 의 격리 대신 닫는 세션의 초안으로 보존하고, 0.5초 대기 대신 **뷰 인계**(뷰가 디바운스 안의 미보고 획을 보고한 뒤 완료를 알림, 획을 긋는 중이면 그 획이 반영된 뒤)를 기다린다. 캔버스 유무를 상태로 둔다(뷰의 생성 · 해체 — 해체 때 미보고 편집 · 받아 둔 인계부터 보고) — 없으면 곧바로 닫고, 있으면 응답이 늦어도 닫지 않고 1초마다 다시 요청한다. 비활성화(`flushPending`)도 인계를 요청한다. **인계 뒤 늦게 온 옛 세대 편집**은 닫은 세션의 초안(그 세션 ID · 근거 · 기준)으로 남기고 저장소 · 새 세션에 섞지 않는다 — 세션을 새로 열 때 세대를 올리고, 편집 문맥에 초안 세션 번호를 붙인다. 닫은 세션의 편집 문맥은 붙은 캔버스가 모두 더 새 세대를 표시했다고 알릴 때까지 둔다(10차 리뷰) — 연달아 바뀌어도(A → B → A) 첫 세션의 늦은 보고가 그 세션의 초안이 된다. 확인 대기 중에 읽은 조회 결과는 섞지 않고 버리되 세션은 유지하고, 마지막으로 알던 내용으로 재합성한 뒤 확인되면 다시 읽는다. 초안 전용 세션 · 보이기만 하는 초안을 이은 절은 지우기 · 기록 복원 메뉴를 띄우지 않는다(③ 에서 버전으로 — 중간 빌드 한정, 아래 "메뉴 숨김") | ✅ **10차 리뷰 보완 반영**(2026-09-21) — 엄격한 초안 읽기(실제 파일 손상 · 권한 · 폴더 오류를 실제 파일로 시험) · 초안 먼저(초안이 내구성 있게 남은 뒤에만 저장소로) · 보내는 중 표식과 행 대조(저장 완료가 불확실한 초안) · 닫은 문맥 유지(A → B → A) · 결정 1(즐겨찾기 · 위젯 보관 · 목록 해제 · 되돌리기 · N-Canvas 저장 · 기록 복원을 쓰기 진입점에서 차단) · 결정 3(DEBUG 소유 주입과 그 표식의 승계). 단위 · 리듀서 · 컨트롤러 시험(Domain 360 · Feature 435 · Settings 41)과 앱 Debug 빌드 통과. **실제 계정 전환으로 확인했다 — ACC-1 2차 1회차**(2026-09-21, 테스트 계획 §5 "ACC-1 2차"): 로그아웃 · 확인 전 필기는 저장소 · 서버로 가지 않았고(F30 막음), 계정 전환으로 저장소 행이 사라져도 초안이 남아 **전송 전 편집을 화면으로 되살렸다**(F29 막음). 주입 세션에서도 보이기만 하는 초안을 이은 절은 저장소에 쓰지 않았다. 그 시험이 찾은 두 가지를 그 자리에서 고쳤다 — **넣은 내용 지문**(`sentFingerprints`)으로 돌아온 행을 가리고, **확인 전 묶음**의 초안을 같은 계정에서 보이기만 하게 했다. 남은 틈: 보이지 않고 남은 초안이 쌓인다(개수 안내 · 복구 진입점은 ④ — 출시 전 필수). 여기에는 **읽지 못해 옆으로 옮긴 초안 파일**(`*.unreadable-*`, 같은 키에 새 초안을 쓸 때 덮지 않고 남긴 것)도 함께 센다 · 저장 완료가 불확실한 초안은 보존 · 로그만이고 화면 안내는 ④ 다 · 인계 재요청의 실제 긴 획 · 멈춘 도구 알림은 기기에서 아직 보지 **이 리뷰에서 확정한 것(다시 결정하지 않는다).**

- **「남은 필기」 의 기준은 "그 장을 다시 열어도 자동으로 표시되지 않는 초안"** 이다. 열린 캔버스의 일시적 상태로 설정 목록이 흔들리지 않게 한다. 문구를 "화면에 보이지 않는" 에서 **"자동으로 표시되지 않는 필사 초안"** 으로 바꾸고, 묶음 통합 판정(P0-2a)부터 맞춘다. → 이 결정으로 `sessionID: nil` 이 "편집 화면과 다를 수 있다" 던 항목은 **사양 확정 + 문구**로 닫힌다.
- **목록에서 빠지는 것이 정상인 예외**: 이미 저장소에 반영된 `settled` 초안, 그리고 접근할 수 없는 계정 묶음. 기준은 **"접근 가능한 초안 중 저장소에 반영되지 않은 것은 캔버스에 표시하거나, 복구 목록에 표시 실패 · 보존 사유와 함께 올린다"** 이다.
- **20초는 이미 §3-1 의 선택형 대기로 결정돼 있다** — 새 결정이 아니라 미구현이다. 「계속 기다리기」 는 별도 버튼 없이 **대기 화면을 유지**하는 동작이면 된다. 강제 한도(120초 등)는 두지 않는다.
- **사용자 결정으로 남은 것 하나**: P0-3 의 반영 경로를 2.0.0 에 넣을지, 아니면 **"앱을 다시 켜야 나타난다"는 임시 동작과 문구를 명시적으로 받아들일지.** 조용한 기본값으로 두지 않는다.

**남은 것(다음 라운드):** ③ 과 같은 시기에 붙일 **④ 의 되살리기 · 귀속 동의** · 결정 2(1.3.0 무계정 legacy 분리) 미구현 ·
최근 5개 지문 제한은 왕복 횟수 기준이 아니다(오프라인에서 여섯 번 넘게 고치면 밀린다 — 파일은 남고 복구 후보 판정만 못 한다) ·
`draftStore == nil` 이면 초안 없이 저장소로 간다(앱은 늘 주입한다) · F25 를 다른 방법으로 볼지 판단.

실제 앱 경로 확인(2026-09-18, 전용 임시 iPad 시뮬레이터 · iCloud 미로그인): 다른 시뮬레이터의 V5 dev 저장소(필사 행 1 · 미반영 WAL 1.1 MB)를

`apply` 의 구현만 버전 추가로 바꾸는 계획은 부족하다는 리뷰를 받아 순서를 다시 정했다. **데이터가 어느 계정 · 어느 편집 기준에 속하는지를 먼저 고정한다.**

- **출시 범위:** ①~⑥ 모두 2.0.0 이다. C2 초안은 따로 커밋해도 되지만 출시 범위에서 빼지 않는다 — `VerseCommitOrder` 는 호출 순서만 고정할 뿐 확정 전 편집을 보존하지 않는다.
- **중간 빌드는 폐기 가능한 시험 데이터로만 검증한다.** 실사용자 TestFlight 에는 ①~⑥ 이 함께 들어간 빌드부터 낸다.
- **저장소 소유 근거(ACC-1)가 핵심 경로다.** 근거가 없으면 모든 세션이 보존만이라, ② 부터는 새 필기가 초안에만 남고 동기화되지 않는다(명시된 개발 상태로 받아들이고, 이를 풀려고 소유 판정을 완화하지 않는다). 근거를 얻는 방법은 실제 계정 전환 실험으로 검증한 것만 채택한다 — 후보(CloudKit 미러링 메타데이터 · 저장소 소유 표식) 모두 **일치만으로는 저장소 전체의 소유를 증명하지 못하고, 불일치는 차단 근거가 된다.** 실험 설계는 [테스트 계획](./icloud-sync-compatibility-test-plan.md) §3-1. ② 의 초안 · 인계 · 직렬화는 근거 없이도 구현 · 시험할 수 있다(시험은 근거를 주입한다).
- **후보 A(미러링 식별)는 소유 근거로 채택하지 않는다(2026-09-18, 9차 리뷰).** ① F25 에서 식별 변경과 행 삭제는 한 단계가 아니었다(옛 행 + 옛 식별 → 행 삭제 → 새 식별 → 새 행) ② F30 은 식별 없는 행을 다음에 로그인한 계정이 가져가는 경로다 ③ 쓰기 직전에 "확인 계정 = 미러링 식별" 을 봐도 그 뒤 미러링 전환과 원자적으로 묶이지 않는다. 그래서 **불일치 탐지(쓰지 않을 이유)에만** 쓴다. 자동 귀속을 보장하려면 **계정별 저장소 격리**나 **명시적 데이터 수용 경계**(식별 없는 데이터는 사용자가 고른 뒤에만 계정 데이터가 된다)를 검토한다. 계정별 저장소도 미러링 연결 수명(연결 · 해제 · 재연결 사이의 쓰기)과 함께 검증한다.
- **보이지 않고 남은 초안(④ — 출시 전 필수).** ② 는 초안을 지우지 않으므로 보이지 않는 초안(기준이 달라짐 · 다른 근거 · 같은 내용)이 쌓인다. 출시 전에 **그 개수를 안내하고 복구 진입점을 둔다** — 설정의 복구 화면(C11 복구 사본 진입점과 같은 자리)에서 계정 묶음(계정 · 계정 미확인 · 이 기기 전용)별로 보이고, 되살리기는 그 시점 계정의 새 버전(그 시점 K)으로 만든다. 장 이동 · 재실행을 반복한 뒤 남는 세션 수 · blob 증가량을 측정한다(테스트 계획 SAVE-C9).
- **메뉴 숨김은 중간 빌드 한정.** 초안 전용 세션 · 보이기만 하는 초안을 이은 절에서 지우기 · 기록 복원을 띄우지 않는 것은 폐기 가능한 데이터로 시험하는 중간 빌드에만 허용한다. 출시 전에는 버전(③ — `clear` · `select`)으로 되살리거나, 숨길 때 사유를 보인다.
- **C9(2.0.0 편집이 1.3.0 에 보이지 않음)는 받아들인다.** 조건: 모든 기기를 업데이트하라는 안내를 두고, 출시 후보에서 legacy 수용 · 구버전 편집 재수신을 검증한다.

**v3 → v4 에서 바뀐 것 (3차 리뷰)**

- **논리 ID 에 종류 · 내용 지문을 넣는다.** `rowUUID` 없는 행을 `설치 ID + 보존 식별` 로만 만들면 같은 행이 A → B 로 바뀌어도 같은 버전 ID 라 불변 버전 규칙과 충돌한다. `legacyDelete` 는 마지막으로 보존한 내용 지문을 함께 넣어 어떤 원본에 대한 삭제인지 고정한다(C3 ⑤).
- **삭제 단계 2 의 부분 성공을 실패로 다루지 않는다.** 기준점 ID 는 작업을 시작할 때 정해 기록하고, 저장 성공 여부가 불확실하면 작업 기록을 지우지 않고 같은 ID 로 조회 · 재시도한다. 단계 완료 표시는 실제 작업을 끝낸 뒤에 하고, 모든 단계는 다시 실행해도 안전해야 한다(멱등).
- **계정 범위를 K 밖으로 넓힌다.** 초안 · 복구 사본 · 격리본 · 보존 기록 · 삭제 작업 기록 · 대상 목록 · 진행 중인 비동기 작업까지 계정에 묶는다. 다른 계정의 작업은 재개하지 않고, 계정을 확인할 수 없으면 서버 정리와 업로드를 보류한다.
- **정리 조건을 명시한다.** 서버 정리는 `K(기기) − K(x)` 안에 **레코드 자체를 받은** 기준점이 있을 때만 한다. 참조로만 아는 기준점은 서버 정리뿐 아니라 **로컬 원본 파괴(보존 기록 · 원시 사본 삭제)도 보류**한다 — 숨김까지만이다.
- **단계 4 의 제외 대상.** 삭제 작업 기록과 K(기기) 는 지우지 않는다. 공유 blob 은 남는 복구 사본 · 격리본이 참조하면 지우지 않는다.
- **복구 사본 용량 · UX.** 사용량을 설정에 보이고 보관본과 격리본을 구분한다. 사용자가 지울 때 "지금 필사"인지 "되살릴 가능성"인지 분명히 한다. 공간이 부족해도 기존 초안 · 사본을 자동으로 지우지 않고 저장 실패를 유지한다. 이전 계정 사본은 섞거나 자동 업로드하지 않는다.
- **중복 후보 표시 · 선택(C7).** 같은 내용 사본은 카드 하나로 보이고, 고르면 묶인 후보 ID 전체를 부모로 기록한다. 선택 중 도착한 후보는 몰래 포함하지 않고, 격리 후보와 정상 후보는 합치지 않는다.

**v2 → v3 에서 바뀐 것 (2차 리뷰):** 일반 확정은 초안의 K 를 잇고 사용자가 새로 한 결정만 그 시점 K 를 쓴다 · K(기기) 를 계정별로 영속화하고 "참조된 기준점은 서버에 반드시 있다"는 설명을 뺐다 · 삭제 작업 기록으로 재개한다 · 복구 사본을 동기화 저장소에 넣기 전에 저장하고 자동 해제하지 않는다 · 보존 식별과 전역 식별자를 나눴다 · "삭제 이전 데이터"를 "그 삭제를 모른 채 작성한 데이터(무효 데이터)"로 바꿨다.

**용어**

- **legacy 행** — `BibleDrawing` 행. 1.3.0 과 이전 2.0.0 TestFlight 빌드가 쓴 v3 행을 포함한다.
- **의도적 버전** — 2.0.0 에서 사용자가 확정한 `edit` · `select` · `clear` 버전. `legacyImport` · `legacyDelete` 는 들지 않는다.
- **후보** — 사용자가 아직 확인 · 선택하지 않은 legacy 버전이나 분기 끝 버전.
- **보존 식별** — 기기 안에서 물리 행 하나를 가리키는 로컬 영속 식별자(저장소 UUID + 기본 키). business `id` 가 같은 두 행도 서로 다르다. 기기 간에는 쓰지 않는다.
- **전역 식별자** — 기기 간에 같은 물리 행을 가리키는 값. 지금은 `rowUUID` 뿐이고 1.3.0 행에는 없다. business `id` 는 유일하지 않을 수 있어 전역 식별자로 쓰지 않는다.
- **내용 지문** — `lineData` 바이트 · `drawingVersion` · 키를 정렬해 다시 인코딩한 레이아웃 메타데이터(F18)의 SHA-256.
- **상태 지문** — 내용 지문 · `isPresent` · `updateDate` · `creationDate` · `translation` 의 SHA-256.
- **K(x) · K(기기)** — 레코드 x 를 만들 때 알던 삭제 기준점 ID 집합, 기기가 지금 아는 집합.
- **받은 기준점 · 참조로만 안 기준점** — 기준점 레코드 자체를 수신한 ID 와, 다른 레코드의 K 에서 이름만 본 ID. 둘 다 판정에는 쓰지만 **원본을 지우는 데는 받은 기준점만 쓴다.**
- **계정 범위** — 저장과 작업이 어느 iCloud 계정에 속하는지 가리키는 값. **키 = SHA-256(컨테이너 ID ‖ 사용자 레코드 이름) 앞 16바이트**(2026-09-18 결정). 식별 값 자체는 로그 · 파일 · 문서에 남기지 않는다. 계정을 확인하지 못한 동안 · 로그인하지 않은 동안 만든 로컬 보존은 계정 범위가 아니라 **"계정 미확인" · "이 기기 전용" 묶음**에 둔다. 초안 · 복구 사본 · 격리본 · 보존 기록 · 삭제 작업 기록 · K(기기) 가 모두 범위를 갖는다.
- **무효 데이터** — K(기기) ⊄ K(x) 인 레코드. 기기가 아는 어떤 삭제를 **모른 채 작성한** 데이터다. 시간상 그 삭제보다 앞섰는지와는 다른 개념이다.

#### C3. 기존 원본 보존과 수용

**목표:** 2.0.0 이 설치된 기기에 있던 legacy 원본과, 그 기기가 이후 받은 legacy 변경 · 상태 · 삭제를 잃지 않는다. 서버에는 다른 기기에서 찾아야 하는 것만 올린다.

**보존 기록 (비동기화 영역)**

| 기록 | 내용 |
|---|---|
| 내용 blob | 내용 지문을 키로 `lineData` · `drawingVersion` · 레이아웃 메타데이터를 한 번만 저장한다. 복구 사본 · 격리본과 함께 쓴다 |
| 관측 로그 | 추가만 한다. 보존 식별, 전역 식별자(있으면), business `id`, 관측 종류(존재 · 삭제), 내용 지문(삭제면 비움), 상태 필드와 상태 지문, 관측 시각, 계기(최초 전환 · 가져오기 · 시작 대조), 관측 시점의 K(기기) |
| 대조 색인 | 보존 식별마다 보존을 끝낸 마지막 상태 지문. 보존 기록을 쓴 뒤에만 갱신한다 |

| 단계 | 규칙 |
|---|---|
| ① 원시 사본 | 새 저장 모델을 처음 쓰는 버전의 첫 실행에서, **`ModelContainer` 를 만들기 전에** 저장소 파일(`sqlite` · `-wal` · `-shm` · 외부 저장 폴더 `.<저장소 이름>_SUPPORT`)을 비동기화 위치로 복사한다. 완료 조건은 SQLite 무결성 검사 통과와, 외부 저장으로 참조된 blob 파일이 모두 있고 읽히는 것이다. **완료하지 못하면 CloudKit 연결과 편집 진입을 하지 않고** 재시도와 공간 확보를 안내한다(MIG-F1 의 막힘 상태와 같은 자리). 2.0.0 에서는 자동 정리하지 않고 전체 삭제 범위에 넣는다 |
| ② 행 추출 | 원시 사본은 건드리지 않고 **작업용 복제본**을 기존 스키마 · 마이그레이션 경로로 CloudKit 없이 연다. SQLite 를 직접 해석하지 않는다. 모든 legacy 행(대표 · 가려진 중복 · 보관 행 · 빈 행)을 **보존 식별마다 따로** 남긴다. 파일 복사는 저장소 UUID 와 기본 키를 유지하지만, 복제본의 마이그레이션 뒤에도 본 저장소와 같은 보존 식별로 대응되는지는 검증한다. 대응이 모호한 행은 합치지 않고 둘 다 보존한다. 중간에 끊기면 대조 색인을 기준으로 이어서 채운다 |
| ③ 지속 대조 | **가져오기 시작 이벤트에서 "보존 필요" 표식을 켠다.** 가져오기가 성공하면 모든 legacy 행의 상태 지문을 대조 색인과 비교해, 다르거나 새로 생긴 행은 보존하고 사라진 행은 삭제 관측으로 남긴다. 그다음 색인을 갱신하고 표식을 끈다. 날짜 · 크기는 먼저 볼 행을 고르는 힌트일 뿐이다. **앱 시작 때도 같은 전체 대조를 한다.** 시작할 때 표식이 켜져 있으면(보존 도중 종료) `ModelContainer` 를 만들기 전에 ① 과 같은 원시 사본을 떠 그 사본으로 먼저 대조한다. 2.0.0 초기에는 전체 지문 대조로 구현하고, 측정 뒤 최적화한다 |
| ④ 서버 수용 | 필요한 절만 따로 올린다. (a) 그 절의 첫 의도적 버전을 확정할 때, 편집 기준이던 legacy 내용을 `legacyImport` 부모로 올린다. (b) 의도적 버전이 있거나 편집 중인 절에서 legacy 변경 · 삭제를 관측하면 `legacyImport` · `legacyDelete` 후보로 올린다(편집 중이면 확정 직후, C7). (c) legacy 행이 둘 이상인 절(R27)은 모든 행을 후보로 올린다. 업로드 묶음에는 총 바이트 상한과 행 수 상한을 함께 둔다(수치는 큰 blob 시험 뒤). 그 밖의 절은 legacy 행이 이미 모든 기기에 보이므로 올리지 않는다 |
| ⑤ 논리 ID | **`rowUUID` 가 있는 행:** `legacy-` + SHA-256(종류 ‖ `rowUUID` ‖ 내용 지문). 기기 간에 결정적이고, 물리 레코드 중복은 읽을 때 합친다(C5). **`rowUUID` 가 없는 행:** `legacy-` + SHA-256(종류 ‖ 수용한 기기의 설치 ID ‖ 보존 식별 ‖ 내용 지문). **내용 지문을 빼지 않는다** — 같은 행이 A → B 로 바뀌면 다른 버전 ID 여야 불변 버전 규칙과 맞는다. **`legacyDelete`** 는 내용이 없으므로 그 행에서 **마지막으로 보존한 내용 지문**을 넣어 어떤 원본에 대한 삭제인지 고정한다. 두 기기가 같은 원본을 올리면 레코드가 둘 생길 수 있다 — **잘못 합치기보다 중복 보존을 택한다.** 표시할 때만 같은 절 · 번역 · 좌표 형식 · 내용 지문인 후보를 한 묶음으로 보이고(C7 중복 후보 표시), 데이터는 합치지 않는다. 상태만 바뀐 관측은 서버에 올리지 않는다 |

**보장하지 않는 것:**
- 2.0.0 설치 전에 덮인 내용
- 두 대조 사이에 구버전끼리 여러 번 덮어 관측하지 못한 중간 내용(C12)
- 가져오기 시작 이벤트를 관측하기 전에 적용된 가져오기 직후 종료된 경우의 그 내용
- 2.0.0 을 한 번도 실행하지 않은 기기에만 있던 내용

**확인할 시험:**
- 서버에 원격 변경이 쌓인 상태에서 업데이트해도 가져오기 전 내용이 남는가
- 외부 저장 blob 이 빠진 사본은 완료로 처리하지 않고, 편집에 진입하지 않는가
- 날짜 · 크기가 같고 내용만 바뀐 행, 상태만 바뀐 행을 잡는가(상태만 바뀌면 blob 중복 없이 로그만 남는가)
- business `id` 와 내용이 같은 서로 다른 두 행이 보존 기록에 둘로 남는가
- 원시 사본 · 작업용 복제본 · 본 저장소에서 같은 행이 같은 보존 식별로 대응되는가
- 보존 도중 종료하면 다음 시작에서 원시 사본으로 먼저 대조하는가
- 1.3.0 편집 · 삭제를 관측하면 후보가 올라가는가
- `rowUUID` 가 있는 행을 두 기기가 동시에 수용하면 논리적으로 하나인가, 없는 행이면 중복 레코드가 생기되 표시에서는 한 묶음인가
- 같은 legacy 행이 A → B 내용으로 바뀌면 서로 다른 버전 ID 가 되는가(앞 내용이 덮이지 않는가)
- 같은 행의 삭제 관측이 마지막 보존 내용과 묶여 다른 삭제 관측과 구분되는가

**정한 것 (리뷰 추천):** 추출은 작업용 복제본을 기존 경로로 연다 · 원시 사본은 2.0.0 에서 자동 정리하지 않는다 · 사본에 실패하면 보호되지 않은 채 연결 · 편집하지 않는다 · 업로드 묶음은 바이트와 행 수 상한을 함께 둔다 · 전역 식별자가 없으면 중복 보존을 택한다 · 논리 ID 에는 종류와 내용 지문을 함께 넣는다(3차 리뷰).

#### C7. 구버전 후속 편집의 표시

**전제:** 2.0.0 은 `BibleDrawing` 에 쓰지 않는다(C9 — 전체 삭제 예외는 제외). 따라서 1.3.0 의 편집은 2.0.0 편집을 본 적 없는 편집이고, 의도적 버전이 있는 절에서 관측한 legacy 변경은 정의상 분기다.

| 절의 상태 | legacy 변경 · 삭제를 관측했을 때 |
|---|---|
| 의도적 버전 없음 · 편집 중 아님 · legacy 행 1개 · 미해결 후보 없음 | 아래 **자동 반영 조건**을 모두 만족하면 표시가 새 legacy 내용을 따른다(삭제면 빈 절). 하나라도 어긋나면 표시를 유지하고 후보로 보류한다 |
| 편집 중 (초안 · 미보고 변경 · 저장 또는 확정 작업 있음) | 표시를 바꾸지 않고 후보를 로컬에 보류한다. **그 편집이 확정되는 즉시** 새 가져오기를 기다리지 않고 보류 후보를 서버 후보로 수용하고(C3 ④b) 분기를 안내한다 |
| 의도적 버전 있음 | 표시를 유지하고, 후보를 수용하고, 분기를 안내한다 |
| legacy 행 2개 이상 또는 미해결 후보 있음 | 표시를 유지하고, 모든 행과 후보를 분기 안내에 보인다(같은 내용의 중복 후보는 한 묶음, 아래 **중복 후보 표시**) |

**자동 반영 조건 (모두 만족):**
1. 그 절에 로컬 초안 · 캔버스 미보고 변경 · 저장 또는 확정 작업이 없다.
2. 이전 legacy 내용과 새 내용(또는 삭제 관측)이 모두 보존 기록에 있다(C3).
3. 그 절에 서로 다른 legacy 행이 없고 미해결 후보가 없다.

**규칙:**
- `legacyImport` 만 있는 절은 "의도적 버전 없음"으로 본다. 원본을 수용했다는 이유로 표시 정책이 바뀌지 않게 하려는 것이다.
- 원본 보존이 먼저이고 표시 결정은 그 뒤다. 표시를 따라가도 이전 내용은 보존 기록에 남는다.
- 도착 순서로 이전 후보를 버리거나 인과를 확정하지 않는다. 자동 반영은 "그 절의 유일한 legacy 행이 지금 담은 내용"을 보여 주는 것이지 후보들 사이의 승자 판정이 아니다.
- 분기 안내에서 하나를 고르면 확인한 끝 버전 · 후보를 부모로 둔 `select` 버전을 만든다(C1). 고르지 않고 닫으면 데이터는 바뀌지 않는다.
- **중복 후보 표시:** 같은 절 · 번역 · 좌표 형식 · 내용 지문인 후보는 **카드 하나**로 보이고, 필요할 때만 "동일 내용 사본 N개"를 펼친다. 같은 내용 사본이 여러 개라는 이유로 실제 편집 충돌처럼 반복해서 알리지 않는다(C3 ⑤ 의 중복 보존이 사용자에게 충돌로 보이지 않게 하려는 것이다).
- **선택 기록:** 고른 카드에 묶인 **후보 ID 전체**를 `select` 버전의 부모로 기록한다. 대표 하나만 처리하면 나머지가 다시 미해결 분기로 남는다.
- **선택 중 도착:** 선택 화면을 여는 시점의 묶음을 고정한다. 그 뒤 도착한 후보는 조용히 그 선택에 포함하지 않고, 이후 후보로 남겨 다시 안내한다.
- **격리 후보 분리:** 삭제로 격리된 후보(C11)는 내용이 같아도 정상 후보와 같은 카드로 합치지 않는다 — 되살리기는 다른 결정이다.
- 라벨이 어긋난 행(F12 · F16)은 따라가도 위치가 어긋나 보일 수 있다. 알려진 제한이며 좌표 복구는 2.1 이다.

**확인할 시험:**
- 편집하지 않은 절, `legacyImport` 만 있는 절이 자동 반영되는가
- 편집 중에 관측한 후보가 확정 직후 새 가져오기 없이 분기로 안내되는가
- 의도적 버전이 있는 절과 R27 중복 절은 분기가 되는가
- 1.3.0 전체 삭제를 관측하면 자동 반영 대상 절은 빈 절이 되고, 의도적 버전이 있는 절은 유지되는가
- 여러 변경이 한 번의 가져오기에 합쳐져도 규칙대로 동작하는가
- 같은 내용 사본이 여러 개여도 카드 하나로 보이고, 고르면 묶인 후보가 **모두** 해결되는가
- 선택 화면을 연 뒤 도착한 후보가 그 선택에 섞이지 않고 다음 안내로 남는가
- 격리 후보와 정상 후보가 내용이 같아도 같은 카드로 합쳐지지 않는가

**정한 것 (리뷰 추천):** 자동 반영 안내는 열린 장의 캔버스가 실제로 바뀔 때만 짧게 하고, 분기 · 오류 안내와 구분한다 · "확인함"은 기기 로컬에 둔다(선택 결과는 `select` 버전으로 동기화된다) · 같은 내용 사본은 한 카드로 묶고 선택은 묶음 전체를 해결한다(3차 리뷰).

#### C11. 전체 삭제

**보장:** 삭제 사실(기준점)을 **수신한** 2.0.0 기기는, **그 삭제를 모른 채 작성한 데이터**를 자동으로 다시 표시하지 않는다. 기준점이 아직 도착하지 않은 기기에서는 보이고 편집될 수 있다.

**보장하지 않는 것:**
- 기준점이 도착하기 전 기기에서의 표시 · 편집
- 작성한 기기를 잃은 뒤(복구 사본이 없는 상태에서) 도착한 삭제로 무효가 된 필기
- 삭제 뒤 구버전 기기가 올린 legacy 행이 정리되면서 그 기기 화면에서 사라지는 것 — 2.0.0 기기의 격리본으로만 되살린다

**기준점 (`DrawingEraseEpoch`, 후보)**
- **필드:** 기준점 ID(UUID), 만들 때 알던 기준점 집합(이전 기준점의 이전 목록까지 펼친 닫힌 집합), 만든 기기, 표시용 시각.
- **추가만 하고 지우지 않는다.** 동시에 만든 기준점은 모두 유효하다.

**K 기록 규칙**

| 무엇을 만들 때 | K |
|---|---|
| 초안을 시작할 때(기준 버전 · legacy 내용을 잡을 때) | 그 시점의 K(기기) |
| 일반 편집을 확정할 때(초안 → 버전) | **초안의 K 를 그대로 잇는다.** 확정 시점의 K(기기)로 바꾸지 않는다 |
| 되살리기 · 분기 선택 · 절 지우기 | 사용자가 그 결정을 한 시점의 K(기기) |
| 즐겨찾기 추가 | 추가한 시점의 K(기기) |
| 복구 사본 | 원본 레코드와 같은 K |
| legacy 행, K 필드가 없는 기존 레코드 | 빈 집합 |

편집 도중 새 기준점을 알게 되면, 그 초안은 무효 데이터로서 아래 처리 표를 따른다.

**계정 범위와 K(기기) 영속화**
- K(기기) 는 비동기화 영역에 **추가만 하는 집합**으로 저장하고, 판정 · 정리보다 먼저 기록한다.
- 들어오는 것: 받은 기준점 레코드, 그 레코드의 이전 집합, 받은 레코드가 K 로 참조한 기준점 ID(받은 것과 참조로만 안 것을 구분해 적는다).
- 한 번 들어온 ID 는 참조한 레코드가 지워져도 빼지 않는다. 재실행 뒤에도 그대로다.
- **계정에 묶이는 것은 K 만이 아니다.** 초안 · 복구 사본 · 격리본 · 보존 기록 · 원시 사본 · 삭제 작업 기록 · 대상 목록 · 진행 중인 비동기 작업까지 **계정 범위**를 함께 기록한다. 시작할 때와 계정 변경을 감지했을 때 현재 계정을 확인하고, **범위가 다른 작업은 재개하지 않는다** — A 계정의 삭제 작업을 B 계정 저장소에서 잇지 않는다(ACC-1 과 함께 검증).
- **계정을 확인할 수 없으면**(로그아웃 · 조회 실패 · 전환 중) 서버 정리와 새 계정으로의 업로드를 **보류**하고 로컬 보존만 이어 간다. 확인된 뒤에 같은 범위의 작업만 잇는다.
- **확인 규칙(2026-09-18 결정):** 앱을 시작할 때와 계정 변경 알림 때 CloudKit 사용자 레코드 ID 를 조회한다(`CloudAccountIdentityClient`). `FileManager.ubiquityIdentityToken` 은 쓰지 않는다 — iCloud Drive 를 끄면 CloudKit 이 동작해도 nil 이다.

  | 조회 결과 | 상태 | 로컬 보존(복구 사본 · 초안) | 서버 정리 · 삭제 작업 · K 갱신 · 버전 확정 |
  |---|---|---|---|
  | 사용자 레코드 이름을 얻음 | 확인됨 | 그 계정 범위 | 한다 — 확인 세대 표를 받아 서버 단계마다 다시 확인한다 |
  | 로그인하지 않음 | 로그인 안 함 | "이 기기 전용" 묶음 | **하지 않는다** — 이전 계정의 저장소가 남아 있을 수 있어, 로컬 삭제가 무엇에 적용되는지는 전체 삭제 연결 단계에서 정한다 |
  | 조회 중 · 조회 실패 · 제한 · 일시 오류 | 확인 전 | "계정 미확인" 묶음 | 보류 |

  - **재확인하는 동안 서버 작업을 잠근다.** 계정 변경 알림을 받거나 다시 조회를 시작하면 확인 세대를 올리고 상태를 "확인 전" 으로 돌린다. 진행 중인 저장 · 삭제는 시작할 때 받은 표(`AccountServerWorkToken`)가 아직 유효한지 서버 단계마다 확인하고, 무효면 멈춘다.
  - **늦게 온 조회 결과는 버린다.** 조회를 기다리는 사이 세대가 바뀌었으면 그 결과로 상태를 덮지 않는다 — A 조회가 늦는 사이 B 확인이 끝났는데 A 결과가 덮으면 이전 계정으로 서버 작업을 하게 된다.
  - **마지막으로 확인한 범위는 참고 정보일 뿐이다.** 앱을 끈 사이 시스템에서 계정을 바꿨을 수 있어, 저장소 내용의 소유를 정하는 근거로 쓰지 않는다.
  - **자동 귀속은 하지 않는다.** 기존 초안 · 사본은 만들 때의 범위를 유지한다. "계정 미확인" · "이 기기 전용" 묶음은 계정이 확인되거나 로그인해도 옮기지 않고, 사용자가 복구 화면에서 명시적으로 되살릴 때만 그 시점 계정의 새 버전(그 시점 K)으로 만든다. 로그인할 때 로컬 K · 삭제 작업 기록도 새 계정으로 옮기지 않는다.
  - 이 규칙은 `AccountScopeProvider` · `AccountScopeResolver` 에 있다. 계정 변경 알림 · 시작 시 조회에 거는 것은 첫 사용처와 함께 한다.
- **참조로만 안 기준점:** 로컬 저장과 서버 전송은 별개라, 기준점 레코드보다 그것을 참조한 레코드가 먼저 올 수 있다. 참조만으로도 판정(숨김)에는 쓴다. 다만 **원본을 없애는 일 — 서버 정리와 로컬 보존 기록 · 원시 사본 삭제 — 은 그 기준점 레코드를 받은 뒤에만 한다.** 잘못된 참조 하나로 계정 데이터가 지워지는 것을 막는 안전장치다.
- **정리 조건:** 레코드 x 를 서버나 로컬 보존에서 지우려면 `K(기기) − K(x)` 안에 **레코드 자체를 받은 기준점**이 하나 이상 있어야 한다. 다른 기준점을 받았다는 이유로, 참조로만 아는 기준점 때문에 무효가 된 레코드를 지우지 않는다.

**판정:** 레코드 x 는 **K(기기) ⊆ K(x)** 일 때만 유효하다. 아니면 무효 데이터다.
- **최초 상태:** 기준점이 없으면 K(기기) 가 빈 집합이라 모든 레코드가 유효하다.
- **단조성:** K(기기) 는 늘기만 하고 K(x) 는 바뀌지 않으므로, 한 번 무효인 레코드는 다시 유효해지지 않는다. 되살리기는 새 레코드다.
- **순서 무관:** 기준점과 레코드가 어떤 순서로 도착해도 같은 결론으로 모인다.
- **동시 삭제:** 같은 이전 상태에서 만든 E1 · E2 는 둘 다 K(기기) 에 들어간다. 서로 모르고 삭제한 뒤 각자 작성한 필기는 양쪽 모두 무효가 된다 — 정책상 의도된 결과이며, 작성한 기기의 복구 사본으로 되살릴 수 있다.
- 판정은 순수 함수로 두고, 도착 순서 순열로 단위 테스트한다.

| 데이터 | 처리 |
|---|---|
| 이 기기가 만든 레코드(복구 사본 있음), 동기화 저장소에 아직 넣지 않은 초안 | **로컬 격리본**으로 표시하고 사용자가 되살리기 · 지우기를 고른다. 내용이 이미 비동기화 영역에 있으므로 서버 정리와 상관없이 남는다. 되살리기는 그 시점 K 로 새 레코드를 만든다 |
| 이 기기가 동기화 저장소에 넣었지만 아직 내보내지 않은 레코드 | 내보내기를 앱이 막는다고 보장하지 않는다. 복구 사본으로 격리 · 선택하고, 서버에 올라가도 읽기 판정과 사후 정리가 최종 방어다 |
| 그 밖의 동기화 레코드(다른 기기가 만든 것) | 표시하지 않는다. **그 레코드를 무효로 만든 기준점을 실제로 받았을 때만**(정리 조건) 서버에서 정리하고, 아니면 숨기기만 한다. 원래 기기의 보존은 그 기기의 복구 사본이 맡는다 |
| 기준점 없는 legacy 행(수신 뒤 남아 있거나 새로 도착) | 자동 표시 · 수용하지 않는다. **격리본을 비동기화 영역에 저장하고 저장이 확인된 뒤에만** 서버에서 정리한다. 공간이 부족하면 정리를 보류하고, 숨긴 채 공간 확보를 안내한다. 안내 문구: "예전 필사가 다시 올라왔거나, 삭제 뒤 구버전 기기에서 새로 쓴 필사일 수 있어요" |
| 이 기기의 보존 기록 · 원시 사본 · 대조 색인 중 무효인 것(기록 시점 K 로 판정) | **정리 조건을 만족할 때만 지운다.** 참조로만 아는 기준점 때문에 무효가 된 것은 숨기기만 하고 남긴다. 공유 blob 은 다른 유효 복구 사본 · 격리본이 참조하면 남긴다 |
| 편집 중인 장 | 해당 절의 초안을 격리하고, 삭제 수신을 알린 뒤 장을 다시 연다 |

**복구 사본 (기기 로컬)**
- 이 기기에서 만드는 버전 · 즐겨찾기는 **동기화 저장소에 넣기 전에** 복구 사본을 내구성 있게 저장한다. 저장하지 못하면 확정하지 않고 저장 실패로 안내한다. 초안은 그대로 남는다.
- **2.0.0 에서는 자동으로 해제하지 않는다.** 이 기기의 전체 삭제 작업과, 사용자가 복구 화면에서 지울 때만 없앤다. 용량을 측정해 2.1 에서 보관 정책을 정한다 — 유한 보관을 택하려면 보호 보장을 낮추는 제품 결정이 따로 필요하다.
- **격리 · 복구 안내:** 설정에 지속적인 복구 진입점을 두고, 격리가 생기면 앱 안에서 안내하고, 기록 화면에서도 들어갈 수 있게 한다. 시작을 막는 반복 팝업은 쓰지 않는다.
- **용량:** 같은 내용 blob 은 내용 지문을 키로 공유하되, 체크포인트가 쌓이며 늘어나는 양을 측정해 기록한다(긴 절 · 장시간 편집 기준). 설정에 **복구 사본 사용량**을 보이고, 정상 보관본과 **삭제 충돌로 생긴 격리본**을 나눠 표시한다.
- **사용자가 지울 때:** "지금 보고 있는 필사를 지우는 것"인지 "되살릴 수 있는 사본만 없애는 것"인지 문구로 구분하고, 되돌릴 수 없다고 알린다.
- **공간 부족:** 이미 있는 초안 · 복구 사본 · 격리본을 자동으로 지워 자리를 만들지 않는다. 새 저장은 실패로 두고 공간 확보를 안내한다.
- **이전 계정:** 다른 계정 범위의 복구 사본 · 격리본은 새 계정 화면에 섞지 않고 자동으로 올리지도 않는다. 2.0.0 에서는 **그 계정으로 돌아왔을 때만** 접근한다.

**④ 복구 화면 (설계 초안, 2026-09-21 — 사용자 결정 반영)**

보이지 않게 남은 것을 사용자가 **보고 · 견주고 · 고르는** 한 자리다. ② 가 초안을 지우지 않고 C11 이 복구 사본을 남기므로, 그 둘과
읽지 못해 옆으로 옮긴 파일까지 같은 화면에서 다룬다. 출시 전 필수다.

*무엇을 보이는가.* 계정 묶음(계정 · 계정 미확인 · 이 기기 전용)으로 나누고, 그 안에서 권 · 장 · 절 차례로 카드를 놓는다. 카드는
저장 시각 · 내용 미리보기 · 분류 · 출처(계정 근거 · K · 주입 표식)를 함께 든다. 안내 대상은 **사용자 판단이 필요한 것**이다.

| 분류 | 무엇 | 화면에서 |
|---|---|---|
| 되살릴 수 있음 | 보낸 행이 사라졌거나(F29) **내가 앞서 넣은 내용으로 돌아온** 초안(`recoverable`) | 지금 필기와 견주어 고른다 |
| 저장 완료가 불확실 | 보내던 중 끝났는데 그 행이 그 뒤로 바뀌었다(`uncertain`) | 같은 비교 화면 + "들어갔는지 확인하지 못했다" 문구 |
| 기준이 달라짐 · 다른 근거 | 그 사이 다른 내용이 들어왔거나 계정 · K 가 달라 보이지 않는 초안(`kept`) | 비교하고 고른다. 되살리면 지금 내용 위에 새 버전이 된다 |
| 읽지 못함 | 깨져서 옆으로 옮긴 파일(`*.unreadable-*`) | 「복구할 수 없음 · 파일은 보관됨」 카드로 보이고 **내보내기**를 둔다(사용자 결정) — 되살리기는 없다 |
| 정리 대상 | 내용이 이미 지금 필기와 같다(`settled`) | **목록에 넣지 않는다**(파일은 남는다) |
| 지금 보이는 중 | 화면에 이어 보이는 초안(`shown` · `showOnly`) | 목록에 넣지 않고, 필요하면 "지금 보고 있음" 으로만 표시한다 |

*어떻게 고르는가.* 카드를 열면 **지금 필기(왼쪽)와 보관된 것(오른쪽)을 나란히** 보이고 각각의 시각 · 출처를 적는다.
「이 필기로 복구」 를 고르면 **그 시점 계정의 새 버전**(③ 의 `edit`, 부모는 지금 끝 버전, K 는 그 시점 K)으로 남긴다 —
**지금 필기도 지우지 않는다**(이력에 남는다). 초안 · 사본도 지우지 않는다. 정리는 사용자가 명시적으로 지울 때만 한다.

*귀속 동의.* 그 초안의 근거가 지금 계정과 다르거나(다른 힌트 · 계정 미확인 · 이 기기 전용 · 시험 주입 표식) 확인할 수 없으면,
되살리기 전에 **"이 필기를 지금 계정으로 가져올까요?"** 를 따로 묻는다. 동의 없이는 되살리지 않는다. 무엇을 · 어느 계정으로 ·
언제 가져왔는지 기록을 남긴다. 다른 계정 묶음은 **그 계정으로 돌아왔을 때만** 연다(C11 과 같다).

*개수 · 용량.* 설정 진입점에 묶음별 개수와 용량을 보이고, 초안 · 복구 사본 · 격리본 · 읽지 못한 파일을 나눠 센다(SAVE-C9 측정).
지우기 문구는 C11 규칙을 따른다 — "지금 보고 있는 필사" 와 "되살릴 수 있는 사본" 을 구분하고 되돌릴 수 없다고 알린다.

*판정은 한 곳에서.* 목록은 편집 화면과 같은 `VerseDraftRecoveryRule.plan` 분류를 쓰고, "지금 필기" 는 ③ 의 공통 조회를 쓴다 —
화면마다 다른 답을 내지 않게 한다.

*진입점.* 설정의 복구 화면(C11 과 같은 자리)이 기본이다. 편집 화면에서는 **절 메뉴에만** 「복구할 수 있는 필기 N」 을 두고 거기서
복구 화면으로 간다(사용자 결정) — 절 번호 옆 표시나 시작을 막는 팝업은 쓰지 않는다.

*순서(사용자 결정).* **읽기 전용부터 먼저 만든다** — 개수 · 용량 안내, 묶음별 목록과 비교, 지우기, 내보내기까지. 쌓이는 초안을 지금
빌드에서도 볼 수 있다. **되살리기 · 귀속 동의는 ③ 의 버전 쓰기와 같은 시기**에 붙인다.

*읽기 전용 단계의 조각.*
1. **조회 — 2026-09-21 됨.** `LocalPreservationWriter.draftBuckets()` · `draftSummary(in:)` · `unreadableDraftFiles(in:)`.
   묶음 · 초안 수 · 바이트 · 읽지 못해 옆으로 옮긴 파일 · **초안이 남은 장**을 **파일만 보고** 센다 — 저장소를 읽지 않으므로
   깨진 초안이 있어도 개수 · 용량은 나온다(그 장을 여는 것은 여전히 막는다).
2. **판정 — 2026-09-21 됨.** `VerseDraftRecoveryQuery.inventory(in:environment:)`.
   - 초안이 남은 **장만** 저장소에서 읽어 편집 화면과 같은 `VerseDraftRecoveryRule.plan` 으로 가른다.
   - **화면에 보이는 것(`shown` · `showOnly`)과 역할이 끝난 것(`settled`)은 목록에서 뺀다.** 남은 것만 까닭
     (`VerseDraftRecoveryReason` — 되살릴 수 있음 · 저장 완료 불확실 · 저장소가 바뀜 · 다른 근거 · 더 새 초안이 보임)과
     그 절의 **지금 필기**(비교의 한쪽)를 함께 든다.
   - 편집 화면이 읽지 않는 묶음(다른 계정 · 이 기기 전용)은 **저장소와 대조하지 않는다** — 지금 저장소는 그 계정의 내용이 아니다.
     세어 보이기만 하고 그 계정으로 돌아왔을 때 연다.
   - **한 장을 읽지 못해도 나머지는 알린다**(그 장은 따로 든다). 아무것도 쓰지 않고 파일도 지우지 않는다.
   - 화면과 목록이 엇갈리지 않게 **같은 규칙을 한 곳**에 뒀다 — `VerseDraftStoreView`(대표 행 · 절 내용 · 행 내용),
     `VerseDraftRecoveryRule.reachesScreen`(확인 전 묶음의 힌트), `DrawingEditEnvironment.readableDraftScopes`(읽는 묶음).
3. **화면(목록) — 2026-09-21 됨.** 설정 → 저장 → **「남은 필기」**(`DraftRecoveryFeature` · `DraftRecoveryView`).
   - 요약: **초안 전체 개수 · 용량**과 **그중 화면에 보이지 않는 것**을 따로 적는다(같은 수로 뭉뚱그리면 보이는 초안까지 사라진 것처럼 읽힌다).
     읽지 못한 파일 수 · 용량, 확인이 필요한 것(되살릴 수 있음 · 저장 완료 불확실) 수도 함께.
   - 묶음 카드를 펼치면 절 카드: **미리보기**(`CarveInkThumbnail`) · 자리(창세기 1:3) · 시각 · 분류 배지 · 시험 주입 배지 ·
     까닭 설명 · 그때의 계정 근거(K 를 모르면 그것도) · **지금 그 절의 상태**(비었는지 · 언제 바뀌었는지).
   - **할 수 없는 것을 먼저 말한다** — "지금은 보기만 할 수 있어요. 되살리기는 준비 중이고, 그동안에도 이 파일들은 지워지지 않아요."
   - 읽지 못한 묶음은 **0개가 아니라 「읽지 못했어요 · 파일은 그대로 있어요」**, 대조하지 못한 장도 따로 적는다.
   - **견주기(2026-09-21 됨)**: 카드를 누르면 **지금 필기(왼쪽)와 보관된 것(오른쪽)**을 나란히, 각각의 시각과 함께 보인다.
     지금 필기는 **그때 그 장만** 읽는다(`VerseDraftRecoveryQuery.currentVerse`) — 목록은 필기 바이트를 들고 있지 않다.
     지금 필기를 읽지 못하면 "없다" 가 아니라 읽지 못했다고 적는다. 견주는 동안 어느 쪽도 바뀌지 않는다.
   - **내보내기 · 지우기(2026-09-21 됨)**: 읽지 못해 옆으로 옮긴 파일에만 둔다. 내보내기(`ShareLink`)를 앞에 두어 먼저 꺼낼 수 있게 하고,
     지우기는 묻고 받은 뒤에만 지운다 — "지금 보고 있는 필사와 남은 초안은 그대로예요 · 지운 파일은 되돌릴 수 없어요".
     **초안을 지우는 길은 이 화면에 없다**(사용자 결정 2026-09-21) — 되살리기(③)가 붙기 전에는 그 초안이 유일한 사본일 수 있다.
     읽는 경계(`VerseDraftRecoveryReading`)와 지우는 경계(`VerseDraftUnreadableCleaning`)를 나눠, 초안을 지우는 호출 자체가 만들어지지 않는다.
4. **절 메뉴 — 2026-09-21 됨.** 그 절에 보이지 않게 남은 초안이 있을 때만 **「남은 필기 N」** 을 띄우고(수는 화면 목록과 같은
   `VerseDraftRecoveryPlan.kept`), 누르면 설정의 「남은 필기」 를 연다. 절 번호 옆 표시나 시작을 막는 팝업은 쓰지 않는다.
   **저장소에 쓰지 않는 절에서도 띄운다** — 그 절이야말로 초안에만 남아 있을 때가 많다(「지우기」 · 「이전 필사」 와 다른 조건이다).
   화면 이름에 맞춰 「복구할 수 있는 필기」 대신 「남은 필기」 로 적는다 — 이 단계에서는 되살리지 않고 보여 주기만 한다.

**삭제 작업 (실행한 기기)**

시작할 때 **삭제 작업 기록**(작업 ID · **미리 정한 기준점 ID** · 계정 범위 · 진행 단계 · 시작 시점 대상 목록)을 비동기화 영역에 먼저 저장한다. 대상 목록은 그 시점 동기화 저장소에 있던 레코드의 보존 식별과 논리 ID 다.

**모든 단계는 다시 실행해도 안전해야 한다(멱등).** 단계 완료 표시는 **실제 작업을 끝낸 뒤에** 기록하고, 표시 전에 앱이 종료돼 같은 단계를 다시 실행해도 결과가 같아야 한다.

1. 열린 장의 미저장분을 처리한다(현행 세대 규칙).
2. 작업 기록에 적어 둔 **같은 기준점 ID** 로, 현재 K(기기) 를 담은 기준점을 동기화 저장소에 저장하고 K(기기) 에 넣는다. ID 를 미리 정해 두므로 재시도해도 기준점이 늘지 않는다. **확실히 실패했을 때만** 중단하고 작업 기록을 지운다. **성공 여부가 불확실하면**(저장은 됐는데 K 기록이 실패, 응답 없음, 확인 불가) **작업 기록을 유지하고** 같은 ID 로 조회해 있으면 K 에 넣고 없으면 다시 저장한다 — 이미 일어난 삭제를 재개할 근거를 없애지 않는다.
3. **시작 시점 대상 목록**과, 진행 중 도착했더라도 판정상 무효인 버전 · 즐겨찾기를 지운다. **새 기준점을 알고 만든 유효 레코드는 도착 시점과 상관없이 지우지 않는다.** 진행 중 새로 도착한 legacy 행은 대상 목록에 없으면 위 legacy 격리 흐름으로 넘긴다. 대상 목록을 기준으로 하므로 여러 번 실행해도 같은 결과다.
4. 이 기기의 로컬 데이터(초안 · 보존 기록 · 원시 사본 · 색인 · 복구 사본 · 격리본 · 위젯)를 **격리 없이** 지운다 — 이 기기에서 사용자가 삭제를 요청했기 때문이다. **지우지 않는 것: 삭제 작업 기록 · K(기기) · 계정 범위 기록** — 완료를 적기 전에 종료돼도 재개할 근거가 남아야 한다. 새 기준점을 알고 만든 것은 남기고, 공유 blob 은 남는 복구 사본 · 격리본이 참조하면 남긴다.
5. 모두 끝나면 작업 기록을 완료로 두고 "이 기기에서 확인한 필사를 모두 지웠어요. 아직 연결되지 않은 기기는 연결되면 정리돼요"를 보인다.

**재개:** 앱이 시작할 때 완료되지 않은 작업 기록이 있으면, 완료 표시가 없는 단계를 처음부터 다시 실행해 이어서 끝낸다. 이때는 수신 기기 규칙이 아니라 실행 기기 규칙을 따른다 — 복구 사본을 격리하지 않고 지운다. **작업 기록의 계정 범위가 지금 계정과 다르면 재개하지 않고**, 그 계정으로 돌아왔을 때 잇는다. 계정을 확인할 수 없으면 서버 작업을 보류하고 기다린다. 끝나기 전에는 완료로 표시하지 않는다. 로컬 저장소 세대(`DrawingStoreGeneration`)는 이 기기 안의 삭제 · 저장 경쟁만 막고, 기기 간 재등장에는 쓰지 않는다.

**확인할 시험:**
- S1~S13 전부
- 삭제 작업: 단계 사이뿐 아니라 **실제 저장 · 삭제 성공 직후 · 단계 기록 직전**에 종료하고 재개 — 같은 단계를 다시 실행해도 안전한가, 기준점이 늘지 않는가
- 같은 지점에서 계정을 전환하면 재개하지 않는가, 원래 계정으로 돌아오면 잇는가
- 단계 4 뒤에도 작업 기록 · K(기기) 가 남아 재개할 수 있는가
- 정리 조건 — 참조로만 아는 기준점으로는 서버 레코드도 로컬 보존 기록도 지우지 않는가
- 공유 blob 을 다른 복구 사본 · 격리본이 참조하면 남기는가
- 복구 사본을 저장하지 못하면 확정하지 않는가
- 공간이 부족할 때 legacy 정리를 보류하고, 기존 초안 · 복구 사본을 자동으로 지우지 않는가
- 계정 전환 시 K(기기) 와 초안 · 복구 사본 · 격리본 · 작업 기록이 모두 분리되는가
- 초안의 K 계승 — 편집 중 기준점을 받은 초안이 새 데이터로 통과하지 않는가
- 판정 함수의 도착 순서 순열 단위 테스트

**정한 것 (리뷰 추천):** 복구 사본은 2.0.0 에서 자동 해제하지 않는다 · 격리 · 복구 진입점은 설정에 상시로 두고, 발생 시 앱 안에서 안내하며, 기록 화면에서도 들어갈 수 있게 하고, 시작을 막는 반복 팝업은 쓰지 않는다 · 보관 기간이 지나 조용히 사라지는 것은 제한으로 받아들이지 않는다 · 삭제한 legacy 해시 목록은 쓰지 않는다 · 기준점 엔티티는 필수 운영 배포 대상이며 실제 스키마로 다시 검증한 뒤 배포한다 · **이전 계정의 복구 사본 · 격리본은 새 계정에 섞거나 올리지 않고 그 계정으로 돌아왔을 때만 접근한다** · 공간이 부족해도 기존 초안 · 사본을 자동으로 지우지 않고 저장 실패를 유지한다(3차 리뷰).
